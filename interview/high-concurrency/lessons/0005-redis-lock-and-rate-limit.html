锁与限流：Redis 最容易被追问的两个“原子性”

这两类题看起来是背命令，实际上考的是并发正确性： 锁会不会误删别人的？任务超时了怎么办？限流在边界会不会放过双倍流量？

30 分钟 前置：Lesson 02、04 产出：锁/限流代码 + 追问答案

本课目标

  • 写出一把“不会误删、不会死锁”的 Redis 锁，并说清它的正确性边界。
  • 讲清 Redlock 的争议，知道什么时候该用 DB 约束/乐观锁而不是 Redis 锁。
  • 区分固定窗口、滑动窗口、令牌桶、漏桶，并能用 Redis + Lua 做分布式限流。

1. 一把合格的分布式锁，要满足什么

  1. 互斥：同一时刻只有一个持有者。
  2. 不死锁：持有者崩溃后，锁能自动释放（TTL）。
  3. 只由持有者释放：不能把别人的锁删掉。
  4. 可续期：任务比 TTL 长时，不能让锁提前失效。

正确的最小写法

import redis
import uuid

r = redis.Redis()
lock_key = "lock:order:123"
token = uuid.uuid4().hex

# 一条命令完成“不存在才设置 + 过期时间”，避免 SETNX 后 EXPIRE 之间崩溃
ok = r.set(lock_key, token, nx=True, px=30_000)
if ok:
    try:
        do_work()
    finally:
        # 只删自己的锁：比较 value 再删除，必须原子
        r.eval(
            """
            if redis.call('get', KEYS[1]) == ARGV[1] then
                return redis.call('del', KEYS[1])
            end
            return 0
            """,
            1, lock_key, token,
        )
三个常见错误
  • SETNX 成功后再单独 EXPIRE：中间崩溃就永久死锁。
  • 解锁直接 DEL：任务超时后锁已属于别人，会误删。
  • value 用固定字符串：无法判断锁是不是自己的。

任务比 TTL 长怎么办

方案一：watchdog 自动续期（如 Redisson 的看门狗）。方案二：把任务拆短，或把 TTL 设得足够长。 续期本身也有风险：进程暂停、网络分区时，续期可能发生在锁已经易主之后。

2. Redlock 与它的争议

Redlock 的思路是：部署 5 个独立的 Redis 主节点，客户端依次加锁， 在多数节点成功且总耗时小于锁有效期时，认为加锁成功；释放时删所有节点。

Martin Kleppmann 的批评核心有两点：

  • 时钟与暂停：进程 GC 暂停、时钟跳变，可能让客户端在锁已过期后继续操作。
  • 没有 fencing token：存储层无法拒绝“旧持有者”的写请求，两个客户端可能同时认为自己持有锁。

他的建议是：如果锁是为了效率（避免重复计算），Redis 锁够用； 如果锁是为了正确性（不能有两个写者），要用带单调递增 fencing token 的方案， 或 ZooKeeper/etcd 这类共识系统。

面试一句话

“Redis 锁适合做效率优化，不适合单独承担强一致。真要对正确性负责， 我会用数据库唯一约束/乐观锁，或者给锁加 fencing token， 让存储层拒绝过期持有者的写。”

3. 限流：四种算法，先看要不要允许突发

算法怎么工作优点缺点 / 适用
固定窗口 每个时间窗计数，超过阈值拒绝 实现最简单，内存小 窗口边界可能放过约 2 倍流量
滑动窗口日志 记录每次请求时间，统计最近 N 秒 精确 内存随请求量增长
滑动窗口计数 当前窗口 + 上一窗口按比例加权 近似且省内存 有误差，边界仍非完全精确
令牌桶 按速率放令牌，请求取令牌；桶可积累 允许突发，工程最常用 要处理桶容量与补充速率
漏桶 请求进桶，按固定速率流出 输出平滑，保护下游 不允许突发，可能增加延迟

Redis + Lua 令牌桶

-- KEYS[1] = bucket key
-- ARGV = capacity, refill_per_sec, now_ms, cost
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local cost = tonumber(ARGV[4])

local data = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1]) or capacity
local ts = tonumber(data[2]) or now
local delta = math.max(0, now - ts) / 1000
tokens = math.min(capacity, tokens + delta * rate)

if tokens < cost then
    redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
    return 0
end

tokens = tokens - cost
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) + 1000)
return 1

这段 Lua 在 Redis 里原子执行，多个应用实例共享同一个桶。 返回 0 时，入口层返回 429 Too Many Requests，并带 Retry-After。

限流放在哪一层

网关做粗粒度（IP、租户、接口），应用做细粒度（用户、业务键）， Redis 做跨实例共享；本地令牌桶可以做第一层，减少 Redis 往返。 只做单机限流，多实例部署后总阈值会被放大。

90 秒口述练习

你要给一个多租户 LLM 应用做限流：每个租户有不同套餐，允许短时突发， 还要防止某个租户把整个服务打满。请说明算法、存储和失败策略。

展开参考答案

算法：“用令牌桶，按租户维度建 key，容量对应套餐允许的突发， 补充速率对应每秒额度。每次调用按权重扣令牌，LLM 可以按 token 数或请求数计费。”

存储：“桶状态放 Redis Hash，Lua 脚本原子地读时间、补令牌、扣减、写回； key 带租户 ID，设置过期时间避免冷租户占内存。”

分层：“网关做 IP/租户粗限流，应用层做用户/接口细限流； 本地桶先挡一层，减少 Redis 热点；Redis 故障时降级为本地限流 + 保守阈值。”

失败策略：“超限返回 429 和 Retry-After；核心租户可以排队， 非核心直接拒绝；同时监控每租户的拒绝率和 Redis 延迟，避免限流本身成为瓶颈。”
