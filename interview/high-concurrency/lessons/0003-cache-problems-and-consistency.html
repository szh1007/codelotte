Lesson 03 · 缓存

穿透、击穿、雪崩：三个词，三套解法

这是 Redis 面试出现频率最高的一组题。难点不在背定义，而在 “看到现象能判断是哪一类”以及“说出方案背后的代价”。

30 分钟 前置：Lesson 02 产出：缓存故障诊断 + 一致性答法

本课目标

  • 用一句话区分穿透、击穿、雪崩，并各说出 2–3 个解法。
  • 讲清 cache-aside 的读写路径，以及“为什么更新 DB 后删缓存而不是更新缓存”。
  • 面对“缓存和数据库一致性”能按一致性要求分层回答，而不是一句“延迟双删”。

1. 先把 cache-aside 的路径画出来

读请求先 GET 缓存
→
命中直接返回
→
未命中查 DB
→
回填SET 缓存 + TTL

写路径通常是：先更新数据库，再删除缓存（不是更新缓存）。 这是最常见的 cache-aside 模式，Redis 官方文档 也是这么描述的：应用负责读写缓存，缓存未命中时回源，写入时让缓存失效。

为什么删缓存而不是更新缓存

更新缓存要处理“两次并发写谁覆盖谁”的顺序问题，还要把 DB 的复杂查询结果重新组装； 删除更简单、幂等，下一次读自然回填。代价是下一次读会 miss，需要防击穿。

2. 穿透：查一个根本不存在的东西

现象：请求的 key 在缓存和 DB 里都不存在。每次请求都穿过缓存打到 DB。 常见于恶意刷不存在的 ID、爬虫、参数错误。

解法：

  • 缓存空值：DB 查不到也写一个短 TTL 的空值（如 30–60 秒），让后续请求命中缓存。
  • 布隆过滤器：写入数据时把 key 放进布隆过滤器；查询前先问它。说“不存在”就一定不存在，说“存在”可能是误判。
  • 参数校验 + 限流：ID 格式、范围、签名校验；对同一用户/IP 的异常请求限流。
布隆过滤器的边界

有假阳性、没有假阴性；删除元素麻烦（需要计数布隆或定期重建）。 面试里主动说“它只能挡掉大部分无效请求，不能当唯一正确性保障”。

3. 击穿：一个热点 key 过期了

现象：某个高频访问的 key 刚好过期，大量并发请求同时未命中，一起打到 DB。 注意是单个热点 key，不是大面积 key。

解法：

  • 互斥重建：只让一个请求拿到 SET NX 锁去查 DB、回填，其他请求短暂等待或返回旧值。
  • 逻辑过期：value 里带一个 expireAt，Redis key 本身不设 TTL；发现逻辑过期后异步刷新，读请求先返回旧值。
  • 永不过期 + 后台刷新：适合变化不频繁、能接受短暂旧值的热点数据。
  • 本地缓存 / 请求合并：同一进程内只发一次回源请求。

互斥锁的代价是延迟和吞吐；逻辑过期的代价是可能返回旧值。面试里要说出你选哪个、为什么。

4. 雪崩：大面积 key 同时失效，或缓存整体挂了

现象：大量 key 在同一时间过期（比如统一设置为 1 小时）， 或者 Redis 集群故障，流量瞬间全部打到 DB，DB 被拖垮，进而拖垮整个系统。

解法：

  • TTL 加随机抖动：不要让一批 key 在同一秒过期。
  • 多级缓存：本地缓存 + Redis，Redis 挂了还有本地兜底（注意一致性）。
  • Redis 高可用：主从 + Sentinel 或 Cluster，避免单点。
  • 限流 + 熔断 + 降级：DB 压力过大时挡住部分请求，返回兜底数据。
  • 预热：大促前把热点数据提前加载，避免冷启动。
问题触发范围一句话记忆首选解法
穿透不存在的 key查了个空气空值缓存 / 布隆过滤器
击穿单个热点 key一个热点刚过期互斥重建 / 逻辑过期
雪崩大量 key 或整个缓存一片同时失效TTL 抖动 / 多级缓存 / 限流降级

5. 缓存一致性：先问要求，再谈方案

“缓存和 DB 怎么保证一致性”没有单一答案。先反问一句： 业务能接受多长时间的旧数据？

  • 能接受秒级/分钟级旧数据：cache-aside + 更新 DB 后删缓存 + TTL 兜底，足够。
  • 不能接受旧数据（余额、库存扣减）：不要把强一致寄托在缓存上；用 DB 事务、唯一约束、版本号、分布式锁，缓存只做读加速。
  • 要读到自己刚写的数据：写后短时间读主库，或写后主动更新/删除缓存，并处理并发回填。

为什么“更新 DB 后删缓存”仍可能不一致

经典竞态：

1. 读请求 A 缓存未命中，读 DB 得到旧值 V1
2. 写请求 B 更新 DB 为 V2，然后删除缓存
3. 读请求 A 把 V1 回填缓存
4. 后续读请求一直读到 V1，直到 TTL 过期

应对手段：

  • 延迟双删：更新 DB 后删一次，延迟一段时间（覆盖一次读回填的窗口）再删一次。能降低概率，但不是强一致。
  • 订阅 binlog：用 Canal / Debezium 监听 DB 变更，发 MQ 异步删缓存。删除动作发生在 DB 提交之后，工程上更可靠。
  • 版本号 / 逻辑过期：缓存 value 带版本，写入时版本递增，回填时旧版本不覆盖新版本。
  • TTL 兜底：无论哪种方案，都保留一个最大过期时间，防止永久脏数据。
面试一句话

“缓存一致性要先分级：大多数读多写少业务接受最终一致，用 cache-aside、 更新 DB 后删缓存、TTL 兜底；对并发回填的脏数据，用延迟双删或订阅 binlog 删缓存。 如果是余额、库存这种强一致场景，我不会让缓存承担正确性，正确性放 DB 事务和约束。”

6. 小测：先判断是哪一类

90 秒口述练习

面试官问：“你们的缓存和数据库一致性怎么保证？” 请按“先问要求 → 常规方案 → 并发兜底 → 强一致场景”四步回答。

展开参考答案

先问要求：“先确认业务能接受多长时间的旧数据。商品详情能接受秒级， 余额和库存不能接受，所以方案要分开。”

常规方案：“读走 cache-aside，未命中查 DB 回填；写先更新 DB， 再删除缓存，不直接更新缓存。所有缓存 key 带 TTL 兜底。”

并发兜底：“更新后删缓存仍有并发回填旧值的窗口， 可以用延迟双删降低概率；更稳的是订阅 binlog，DB 提交后发 MQ 删缓存； 缓存 value 带版本号，旧版本不覆盖新版本。”

强一致场景：“库存、余额这类不让缓存承担正确性： 扣减走 DB 事务 + 条件更新/唯一约束，缓存只做展示加速； 需要读己之写就短时间读主库。”

收尾：“所以我的答案是最终一致为主、强一致场景下缓存不参与正确性， 再用 TTL 和监控兜底。”
