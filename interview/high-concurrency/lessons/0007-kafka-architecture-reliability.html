Lesson 07 · Kafka

Kafka 一张图：分区、副本、ISR、消费者组

Kafka 的面试题高度集中：为什么快、消息会不会丢、会不会重复、怎么保证顺序、积压怎么办。 这一课把这些问题串成一条因果链，而不是五个孤立答案。

本课目标

  • 画出 Kafka 的核心结构：broker、topic、partition、replica、offset、consumer group。
  • 讲清 acks、ISR、min.insync.replicas 如何决定“消息不丢”。
  • 回答不丢、不重、有序、积压四连问，并知道 exactly-once 的边界。

1. 一张图看懂 Kafka

Producer按 key 选分区，批量发送
→
Topic / Partition追加写日志，leader 接待
→
Replicafollower 拉取，ISR 同步
→
Consumer Group按 offset 拉取
  • Broker：一个 Kafka 节点；多个 broker 组成集群。
  • Topic：逻辑上的消息类别；Partition：物理上的有序日志，Kafka 的并行单位。
  • Offset：消费者在分区里的位置；提交 offset 表示“我处理到哪了”。
  • Replica：每个分区有 leader 和 follower；leader 处理读写，follower 复制。
  • Consumer Group：同一 group 内，一个分区只会分给一个消费者；不同 group 各自独立消费全量。
  • Controller / KRaft：管理集群元数据和 leader 选举；新版本用 KRaft 替代 ZooKeeper。
为什么是分区，不是全局有序

分区让吞吐可以水平扩展；代价是 Kafka 只保证分区内有序。 要全局有序就只能单分区，吞吐会被锁死。所以业务上通常按订单 ID / 用户 ID 做 key， 让同一业务实体落到同一分区。

2. 为什么快：顺序写 + 批量 + 零拷贝

  1. 追加写日志：消息顺序追加到分区文件，磁盘顺序写远快于随机写。
  2. Page cache：broker 大量依赖操作系统页缓存，读写都在内存里完成，再异步刷盘。
  3. 批量 + 压缩：producer 攒 batch，broker 存压缩后的批次，网络和磁盘都更省。
  4. 零拷贝（sendfile）：消费时把页缓存直接送到 socket，减少用户态拷贝；TLS/压缩等场景可能退化。
  5. 分区并行：多个分区分布在不同 broker，生产和消费都能并行。
  6. Pull 模型：消费者按自己的速率拉取，天然有背压。

3. 写入可靠性：acks、ISR、min.insync.replicas

配置含义取舍
acks=0 producer 发出去就认为成功 最快，可能丢
acks=1 leader 写入成功即返回 折中；leader 挂了、follower 没同步会丢
acks=all ISR 中所有副本都写入才返回 最安全，延迟最高
replication.factor=3 每个分区 3 个副本 容忍 1–2 个 broker 故障，成本更高
min.insync.replicas=2 至少 2 个 ISR 副本确认才算成功 只剩 1 个副本时写入报错，而不是静默丢
unclean.leader.election=false 不让落后太多的副本当 leader 牺牲可用性，避免数据回退

经典组合：RF=3 + min.insync.replicas=2 + acks=all。 挂 1 个 broker 仍能写；挂 2 个就拒绝写，保护数据不丢。

幂等 producer：enable.idempotence=true 后，producer 带 PID + 序列号， broker 会去重重试造成的重复。它解决的是“producer 重试导致的重复”， 不解决跨进程重启、跨系统写入的重复。

4. 消费可靠性：消费者组与 offset

  • 同一 group 内，一个分区只会被一个消费者消费；消费者数超过分区数，多出来的会空闲。
  • 消费者加入/离开、分区变化、心跳超时、max.poll.interval.ms 超时，都会触发 rebalance。
  • enable.auto.commit=true 可能在处理前提交 offset，导致消息丢失；要“至少一次”，用手动提交，处理成功后再 commit。
  • Rebalance 期间消费会暂停；用 cooperative sticky、静态成员、合理超时减少抖动。
  • auto.offset.reset 只在没有已提交 offset 时生效：earliest 从头，latest 从最新。

5. 投递语义：三种，不要混着说

语义怎么做到结果
At most once 先提交 offset，再处理 可能丢，不重复
At least once 处理成功后再提交 offset；失败重试 不丢，可能重复（默认）
Exactly once 幂等 producer + 事务 + read_committed Kafka 内部读写不重不丢；外部系统要配合

Kafka 的 exactly-once 主要覆盖“从 Kafka 读 → 处理 → 写回 Kafka”的链路。 如果最后写的是 MySQL、Redis 或第三方 API，仍需要幂等 sink 或事务消息/Outbox 来保证端到端不重。

四条面试必答

  1. 不丢：producer acks=all + 重试 + 幂等；broker RF=3、min.insync=2、unclean.leader.election=false；consumer 处理成功后再提交 offset。
  2. 不重：默认 at-least-once，消费端做幂等：业务唯一键、去重表、状态机条件更新、版本号。
  3. 有序：同一业务 key 发到同一分区；一个分区同一时刻只被一个消费者处理；不要追求全局有序。
  4. 积压：看 lag → 判断是生产突增还是消费变慢 → 扩消费者（不超过分区数）→ 增加分区/批处理/异步化 → 降级或转存 → 死信。

6. 积压：先定位，再扩容

看 lag生产 offset − 消费 offset
→
定位突增 / 消费慢 / 分区倾斜
→
扩容消费者 ≤ 分区数
→
兜底降级 / 转存 / 死信
  • 消费者数不能超过分区数；超过只是多几个空闲实例。
  • 增加分区可以提升并行度，但会改变 key 的分区映射，影响既有顺序；不要在高峰随意加。
  • 如果消费逻辑里有同步 HTTP/DB 慢调用，先优化下游或改异步，不要盲目加消费者。
  • 积压严重时可以把消息临时转存到另一个 topic/对象存储，先恢复主链路，再慢慢补。

2 分钟口述练习

面试官问：“Kafka 怎么保证消息不丢？” 请按“生产者 → broker → 消费者 → 端到端验证”四段回答。

展开参考答案

生产者：“acks=all，失败重试，开启幂等 producer 防止重试重复； 设置合理的 delivery.timeout 和 retries，不要一失败就丢。”

Broker：“副本数 3，min.insync.replicas=2，acks=all 时至少两个 ISR 确认； unclean.leader.election=false，避免落后副本当 leader 导致数据回退； 再配合磁盘和页缓存监控。”

消费者：“关闭自动提交，业务处理成功后再提交 offset； 失败重试或进死信；消费端幂等，接受 at-least-once 的重复。”

端到端：“监控 producer 错误率、ISR 收缩、consumer lag 和死信量； 定期做故障演练和消息对账。Kafka 的 exactly-once 只在 Kafka 内部链路成立， 写到外部系统仍要靠幂等或事务消息。”
