Lesson 02 · Redis

Redis 不是只有 String：一张表记住 8 种结构

面试里 Redis 的第一层追问永远是“为什么快”和“这个场景用什么结构”。 这一课把这两个问题一次讲透，并给你一个 10 秒选结构的判断法。

25 分钟 前置：Lesson 01 产出：结构选型直觉

本课目标

  • 用 4 个原因解释 Redis 为什么快，并说清“单线程”到底指什么。
  • 记住 8 种核心结构的语义、命令和典型场景。
  • 看到“排行榜 / 去重 / 计数 / 队列 / UV”能在 10 秒内选对结构。

1. Redis 是什么，不是什么

Redis 是一个内存键值数据库，支持持久化、主从复制、Sentinel 高可用和 Cluster 分片。 它常被当作缓存，但它的能力不止缓存：计数器、排行榜、分布式锁、限流、轻量消息队列都能做。

不要把它说成“万能数据库”

Redis 的数据主要在内存，成本高；持久化是异步/准实时，不能当强一致的唯一数据源； 大 key、热 key、缓存击穿都会让它变成故障源。面试里主动说这些边界，比只夸它快更加分。

2. 为什么快：四个原因 + 一个澄清

  1. 纯内存操作：大部分命令是内存读写，不走磁盘。
  2. 事件循环 + IO 多路复用：单线程用 epoll/kqueue 同时监听大量连接，避免“一个连接一个线程”的切换成本。
  3. 命令执行不加锁：命令在单线程里串行执行，天然没有多线程竞争和锁开销。
  4. 高效的数据结构：小集合用 listpack/intset 等紧凑编码，大集合用跳表、哈希表，按规模切换。
澄清：单线程指命令执行

Redis 6 开始用多线程处理网络读写，但命令执行仍然是单线程。 所以“Redis 单线程”不等于“整个进程只有一个线程”；它也不等于“单线程一定比多线程快”， 而是“单线程省掉了锁和上下文切换，瓶颈通常在网络和内存”。

对应的面试追问是“那 Redis 的瓶颈在哪？”答案：网络带宽、CPU（复杂命令）、大 key、慢查询、 内存容量和持久化 fork。解决办法是 pipeline、拆分 big key、读写分离、Cluster 分片、避免 KEYS * / FLUSHALL 这类阻塞命令。

3. 八种结构：语义 + 命令 + 场景

结构核心命令典型场景注意点
String SET GET INCR SET NX PX SETBIT 缓存 JSON、计数器、分布式锁、位图签到 value 上限 512 MB；大字符串是 big key
Hash HSET HGET HGETALL HINCRBY 对象字段、用户资料、会话、部分更新 字段很多时不要 HGETALL；按字段读
List LPUSH RPUSH LPOP BRPOP 简单队列/栈、最新列表、时间线 阻塞弹出不保证可靠消费；可靠队列用 Stream
Set SADD SISMEMBER SINTER SCARD 去重、标签、共同好友、抽奖、点赞集合 大集合的 SINTER 可能很慢
ZSet ZADD ZRANGE ZRANGEBYSCORE ZINCRBY 排行榜、延迟队列、滑动窗口限流 score 相同按 member 排序；注意大 ZSet 的范围查询
Bitmap SETBIT GETBIT BITCOUNT BITOP 签到、DAU、布尔标记、布隆过滤器思路 按用户 ID 映射位偏移；ID 太稀疏会浪费内存
HyperLogLog PFADD PFCOUNT PFMERGE 近似 UV、独立访客数、基数统计 只给近似值（标准误差约 0.81%），拿不到成员
Stream XADD XREAD XGROUP XACK 轻量消息队列、消费组、待处理列表 不是 Kafka 替代品；吞吐和保留策略按场景评估

10 秒选结构

  • 要计数/自增 → String（INCR）。
  • 要存一个对象的多个字段 → Hash。
  • 要去重/判断存在/交并差 → Set。
  • 要排序/排名/按分数范围取 → ZSet。
  • 要队列 → List（简单）或 Stream（要消费组/ACK）。
  • 要布尔标记/签到 → Bitmap。
  • 要近似 UV → HyperLogLog。
面试一句话

“Redis 的结构选型本质是看访问模式：计数用 String，对象用 Hash， 去重用 Set，排序用 ZSet，队列用 List/Stream，UV 用 HyperLogLog。 结构选错，后面靠加机器也救不回来。”

4. 编码、big key 与热 key

编码

Redis 会按集合大小自动切换编码。小 Hash 用 listpack，小 Set 用 intset/listpack， 小 ZSet 用 listpack，大 ZSet 才用跳表 + 字典。你可以用 OBJECT ENCODING key 查看。 这也是为什么“同样 1 万个 key，有的省内存、有的费内存”。

big key

经验阈值：String 超过 10 KB，或集合元素超过 5000 个，就值得警惕。 危害是：单次操作耗时长、网络包大、删除时阻塞、Cluster 里造成数据倾斜。 处理：拆成多个 key、用 UNLINK 异步删除、压缩 value、设置 TTL、用 redis-cli --bigkeys 定期扫描。

热 key

某个 key 的访问量远超其他 key，可能把单个分片打满。处理：本地缓存、key 拆分成多个副本、 读副本分担、请求合并（singleflight）、限流。面试里先问“热到什么程度”，再谈方案。

5. key 设计与 TTL

# 推荐：业务:实体:id:字段
order:123:status
user:456:profile
stock:sku:789

# Cluster 下需要多 key 同槽时，用 hash tag
{user:456}:profile
{user:456}:sessions
  • 所有缓存 key 都要有 TTL；TTL 加随机抖动，避免同一时刻集体过期。
  • 不要用 KEYS * 扫全库；用 SCAN 渐进遍历。
  • Cluster 下多 key 操作必须同槽；跨槽用业务拆分或 hash tag。

90 秒口述练习

设计一个帖子点赞系统：要显示点赞数、判断当前用户是否点赞、按热度排序。 请说明 Redis 用什么结构、写路径怎么走、如何防止重复点赞。

展开参考答案

结构：每篇帖子一个 Set like:post:{id} 存点赞用户， 用 SADD 去重、SISMEMBER 判断是否点过、SCARD 取点赞数； 热度榜用 ZSet hot:posts，ZINCRBY 加分、ZREVRANGE 取 Top N。

写路径：点赞请求先校验登录和帖子状态，再执行 SADD；如果返回 1，说明是新点赞，才 ZINCRBY 加热度， 并异步发 MQ 事件落 DB。取消点赞 SREM，返回 1 才减热度。

幂等：Set 天然去重，重复点赞不会重复计数；DB 侧再用 (user_id, post_id) 唯一索引兜底。MQ 消费失败重试也安全。

规模与兜底：大帖子的 Set 可能很大，可按帖子 ID 分片或只保留近期用户； 热帖用本地缓存 + 请求合并；Redis 挂了降级为“点赞数延迟展示”，不阻塞主流程。
