Lesson 11 · 结合项目

把你的 Agent 项目讲成高并发系统

面试官问 Redis/Kafka，不一定会问电商；他更可能问“你的 Agent 服务怎么扛住很多用户”。 这一课把前 10 课映射到 AI 后端，并给你一套诚实的表达方式。

35 分钟 前置：Lesson 01–10 产出：项目叙事 + 模拟追问

本课目标

  • 说清 AI/Agent 后端的并发特点和 Python 的边界：瓶颈在 I/O 和外部 API，不在 CPU。
  • 把 Redis / Kafka / RabbitMQ 映射到会话缓存、租户限流、任务队列、用量事件等具体位置。
  • 用“设计过 / 本地跑过 / 没有生产经验”的诚实框架回答项目追问。

1. AI/Agent 后端和电商高并发有什么不同

维度典型电商AI/Agent 后端
请求耗时几十到几百 ms几秒到几十秒，流式输出
瓶颈DB 写、热点读外部 LLM API、token 成本、并发配额
并发模型线程/连接池asyncio + 多 worker；I/O 等待为主
失败代价超时、重复下单重复扣费、上下文丢失、工具副作用
一致性库存不能超卖会话状态、用量计费、工具执行结果

你已经在面试材料里讲过 Python 的 GIL、asyncio 和 FastAPI： asyncio 解决的是“等 I/O 时切走”，不解决 CPU 并行。 放到高并发语境里就是：LLM 调用是 I/O 密集型，应该用异步客户端 + 连接池 + 多 worker， 而不是给每个请求开线程硬扛。

2. 中间件映射：每个组件放在哪

需求用什么怎么用追问点
会话/上下文缓存 Redis Hash / String 按 session:{id} 存最近上下文，TTL 控制内存 一致性、隐私、租户隔离、缓存击穿
相同请求的响应缓存 Redis String 对确定性请求做 exact-match 缓存，key 含模型/参数/租户 命中率、失效、语义缓存误命中
租户限流/配额 Redis + Lua 令牌桶 按 tenant/user 维度扣令牌，超限 429 突发、热点、Redis 故障降级
预算/并发锁 Redis SET NX PX 防止同一会话重复执行、控制单租户并发 锁的正确性、超时、fencing
长任务/评测任务 Kafka / RabbitMQ / Redis Stream 提交任务后异步执行，状态写 Redis/DB 重复消费、顺序、积压、死信
工具调用/审计事件 Kafka 按 session_id 分区，事件可重放 不丢、顺序、保留周期、隐私
用量计费 Kafka + 幂等聚合 每次调用发 usage 事件，异步聚合到账单 重复计费、延迟、对账
失败重试/延迟 RabbitMQ DLX / RocketMQ 延迟 工具失败延迟重试，超限进死信 重试风暴、幂等、顺序
一条重要边界

不要用 Kafka 做请求-响应。用户等的是流式 token，不是异步消息； Kafka 适合“事件、任务、审计、计费”，不适合“这个请求的实时回答”。 请求-响应走 HTTP/SSE，异步副作用走 MQ。

3. 设计题：10 万用户同时用你的 Agent，怎么扛

入口
鉴权 + 租户限流 + 配额 网关校验 API Key/租户；Redis 令牌桶按租户限流；超限 429 + Retry-After；流式请求用 SSE。
应用
无状态 FastAPI/uvicorn 多 worker asyncio + 异步 HTTP 客户端连接池；每请求超时和取消；会话状态外置到 Redis；水平扩容。
缓存
会话 + 精确响应缓存 上下文按 session 缓存；确定性请求做 exact-match；语义缓存要加租户隔离和相似度阈值，避免误命中。
队列
长任务 / 评测 / 用量事件 Kafka 按 session/tenant 分区；工具调用事件可重放；失败进死信；消费者幂等。
保护
LLM 供应商熔断 + 降级 + 成本预算 供应商限流/超时时熔断，切备用模型；队列+429 做背压；按租户预算硬止损。
观测
TTFT、tokens/s、成本、错误率、队列 lag 按租户/模型维度看板；追踪一次请求的模型、工具、缓存命中；告警到成本异常和 P99。

4. 诚实表达：没有生产经验怎么说

不要说“我在项目里用过”。推荐三段式：

“我在 codelotte 里没有生产级的 Redis/Kafka 使用。为了回答这类问题，我做了两件事： 一是按 Agent 的业务链路设计了缓存、限流和异步任务方案； 二是在本地用 Docker 跑了 Redis 缓存和 Kafka 生产消费的最小实验。 所以我能讲清楚设计和取舍，但不会声称我有大规模生产运维经验。”

这句话不会扣分，反而会加分：它证明你知道边界，也证明你不是背题库。 接下来面试官通常会问“那你设计一下”，你就用上面的分层答。

5. 30 分钟本地实验（可选，但强烈建议）

目的不是学会运维，而是让你能说“我本地跑过”。只需要 Docker。 

# Redis
docker run -d --name hc-redis -p 6379:6379 redis:7-alpine
docker exec -it hc-redis redis-cli ping

# Kafka（官方单节点镜像；若宿主机连不上，见下面的说明）
docker run -d --name hc-kafka -p 9092:9092 apache/kafka:4.4.0

# 在容器内创建 topic、生产、消费
docker exec -it hc-kafka /opt/kafka/bin/kafka-topics.sh \
  --create --topic demo --bootstrap-server localhost:9092
docker exec -it hc-kafka /opt/kafka/bin/kafka-console-producer.sh \
  --topic demo --bootstrap-server localhost:9092
docker exec -it hc-kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --topic demo --bootstrap-server localhost:9092 --from-beginning
# Python 侧最小验证
pip install redis confluent-kafka

# Redis 缓存
python -c "import redis; r=redis.Redis(); r.set('k','v',ex=60); print(r.get('k'))"

# Kafka 生产/消费（宿主机连 9092；连不上就用容器内 console 工具）
实验边界

单节点 Kafka 不代表生产可靠性；它只证明你跑通过生产/消费/topic。 面试时说“本地单节点实验”，不要说“搭过生产集群”。

6. 模拟面试：10 道项目追问

先自己回答，再看“关键点”。每题按 4 分制自评：结构、数字、取舍、失败场景。

1. 你的 Agent 项目哪里适合用 Redis？为什么？
关键点：会话/上下文缓存、租户限流、任务状态、幂等键；说清 TTL、租户隔离、Redis 挂了怎么降级。
为什么不用本地内存？多实例不一致、重启丢失。
2. 10 万用户同时用，你怎么限流？
关键点：租户/用户维度令牌桶、Redis Lua、网关+应用两层、429 + Retry-After、Redis 故障降级本地限流。
热点租户把 Redis 打满怎么办？本地桶 + 分片 + 预算。
3. LLM 响应很慢，怎么提高并发？
关键点：I/O 密集，用 asyncio + 异步客户端 + 连接池；uvicorn 多 worker；流式输出；超时/取消；不要把慢调用放在事件循环里阻塞。
GIL 不影响吗？I/O 等待时释放，CPU 密集才受限。
4. 工具调用失败或重复怎么办？
关键点：工具调用幂等键、状态机、重试 + 退避 + jitter、死信；有副作用的工具（发邮件、扣款）必须幂等。
重试会不会重复扣费？幂等键 + 服务端去重。
5. 会话上下文怎么缓存？一致性怎么保证？
关键点：Redis Hash/String 存最近上下文，TTL；写入后删缓存或版本号；多实例共享；隐私和租户隔离。
缓存丢了怎么办？从会话存储/DB 重建，允许降级。
6. 怎么统计每个租户的 token 成本和配额？
关键点：每次调用发 usage 事件到 Kafka，按 tenant 分区；异步聚合；幂等去重；预算超限在入口拦截。
重复计费怎么办？事件 ID 去重 + 对账。
7. 为什么不用 Kafka 做请求-响应？
关键点：用户要实时流式回答，Kafka 是异步事件/任务；请求-响应走 HTTP/SSE；Kafka 用于副作用、审计、计费。
那 Kafka 在你项目里到底干嘛？事件、任务、用量、重放。
8. LLM 供应商限流/故障，消息积压怎么办？
关键点：熔断 + 备用模型 + 队列 + 429 背压；消费者限速；死信；按租户公平调度；监控 lag。
降级会不会影响付费用户？分层降级 + 预算。
9. Agent 场景的缓存穿透/雪崩怎么体现？
关键点：不存在的 session/工具结果反复查 DB；热点系统提示/模型配置同时过期；空值缓存、单飞、TTL 抖动、本地缓存。
语义缓存误命中怎么办？租户隔离 + 阈值 + 可回滚。
10. 你说没用过 Redis/Kafka，怎么保证设计可信？
关键点：诚实说明边界；讲设计取舍；讲本地实验；讲失败场景和验证方法；不编造生产数字。
那你怎么验证？本地压测、故障注入、日志指标。

7. 小测：映射是否合理

Agent 的会话上下文要跨多实例共享，优先放哪里？

统计每个租户的 token 用量，最适合用？

3 分钟模拟面试

面试官：“你说说，如果 10 万用户同时用你的 Agent 服务，你怎么设计？ 中间件分别放在哪？哪里可能先崩？”

展开参考答案

先量化：“10 万在线不等于 10 万 QPS。先估算同时活跃请求、 平均会话时长和 LLM 调用频率，再算峰值 QPS、并发连接和 token 成本。”

入口：“网关鉴权，Redis 令牌桶按租户限流和配额，超限 429； 流式回答走 SSE，避免长连接占满线程。”

应用：“FastAPI/uvicorn 多 worker，asyncio + 异步 LLM 客户端连接池； 每请求超时和取消；会话外置 Redis，应用无状态，水平扩容。”

缓存：“会话上下文按 session 缓存；确定性请求做 exact-match； 语义缓存要租户隔离和阈值，避免误命中。”

异步：“长任务、评测、用量事件走 Kafka；按 session/tenant 分区； 消费端幂等；失败进死信；Kafka 不做请求-响应。”

先崩的点：“最可能是外部 LLM 配额和成本，其次是 Redis 热 key、 DB 连接池、Kafka 积压。所以要有熔断、备用模型、队列背压、预算硬止损和 TTFT/成本/ lag 监控。”
