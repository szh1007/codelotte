Lesson 06 · 消息队列

为什么上 MQ：三种收益，四种代价

面试官问“为什么要用消息队列”，最差的回答是“为了解耦”。 好的回答会接着说：解耦换来什么、代价是什么、什么场景不该用。

25 分钟 前置：Lesson 01 产出：MQ 选型答法

本课目标

  • 用“解耦、异步、削峰”解释 MQ 的收益，并各举一个业务例子。
  • 说出 MQ 带来的四种代价，知道什么时候不该上 MQ。
  • 按吞吐、路由、延迟、事务、顺序、生态对比 Kafka / RabbitMQ / RocketMQ。

1. 三种收益：解耦、异步、削峰

解耦

订单服务创建订单后，不需要知道后面有多少消费者：积分、短信、报表、风控、推荐。 新增一个消费者，只订阅 topic，不改订单服务。

订单服务只发 OrderCreated
→
MQ保存事件
→
积分 / 短信 / 报表各自订阅

异步

同步调用三个下游，每个 200 ms，用户要等 600 ms；改成“主流程写库 + 发 MQ”， 主路径可能只要 200 ms，剩下的在后台完成。 

同步：创建订单 200ms + 积分 200ms + 短信 200ms + 报表 200ms = 800ms
异步：创建订单 200ms + 发消息 10ms = 210ms，其余后台处理

削峰

秒杀瞬时 10 万 QPS，DB 只能扛 2 千。MQ 把请求缓冲起来，消费者按 DB 能承受的速率处理。 代价是用户等待时间变长，且要处理“消息积压”和“最终一致”。

2. 四种代价：不要只讲好处

代价具体表现应对
最终一致 订单已创建，积分还没到账；用户看到的状态短暂不一致 状态机、补偿、对账、前端提示“处理中”
重复消费 网络超时、重试、offset 提交失败，消息可能被处理两次 业务唯一键、幂等表、状态机条件更新
顺序问题 同一订单的创建、支付、取消消息乱序 按业务键分区、单分区单消费者、序列号
运维复杂度 积压、死信、重平衡、磁盘、监控、升级 容量规划、lag 监控、DLQ、演练
什么时候不该上 MQ
  • 业务要求强一致、同步返回结果（比如扣款结果必须立刻知道）。
  • 调用关系简单、量很小，引入 MQ 只是增加故障面。
  • 团队没有能力维护 MQ 的积压、死信、重平衡和监控。
  • 用 MQ 来掩盖下游本身就应该优化的问题（慢 SQL、N+1）。

3. 队列模型 vs 日志模型

队列模型（RabbitMQ 典型）日志模型（Kafka 典型）
消息消费后通常从队列删除保留在日志中，按 offset 消费
重复读不支持（除非重新入队）可以重置 offset 重放
路由exchange + routing key，灵活topic + partition，相对简单
吞吐中等，单条确认高，批量 + 顺序写
典型场景业务解耦、任务队列、复杂路由日志、事件流、指标、削峰、重放

还有一点常被忽略：push vs pull。RabbitMQ 可以 push 给消费者； Kafka 是消费者 pull，消费者能自己控制速率，天然有背压（但也会积压）。

4. 三家怎么选

维度KafkaRabbitMQRocketMQ
强项 高吞吐、日志保留、重放、流处理生态 灵活路由、低延迟、单条确认、DLX/优先级 高吞吐、事务消息、延迟消息、顺序消息
弱项 原生延迟/优先级弱；分区过多有开销 吞吐相对低；大量积压时性能下降 生态和国际化不如 Kafka；运维依赖 NameServer
典型场景 日志、埋点、事件流、指标、削峰 业务解耦、任务队列、复杂路由、RPC 异步化 电商交易、订单、支付、延迟取消
一句话 “能存能重放的分布式日志” “路由灵活的业务消息总线” “为交易场景补了事务和延迟”

如果规模很小、只想在 Redis 里做个轻量队列，可以用 Redis Stream： 有消费组、pending list 和 ACK，但不要把它当 Kafka 的替代品—— 保留策略、吞吐、生态和运维能力都不是一个量级。

面试一句话

“选型先看三件事：吞吐和保留、路由和延迟、事务和顺序。 Kafka 适合高吞吐事件流和重放；RabbitMQ 适合复杂路由和业务任务； RocketMQ 适合交易场景的事务消息、延迟消息和顺序消息。 如果只是小规模异步，Redis Stream 或直接线程池可能更划算。”

90 秒口述练习

面试官问：“你们的订单系统为什么要上 MQ？不上行不行？” 请按“收益 → 代价 → 替代方案 → 结论”回答。

展开参考答案

收益：“订单创建后要发积分、短信、报表、风控。同步调用会让主链路变长， 任一消费者故障都会拖慢下单；上 MQ 后主流程只写订单和发事件， 新增消费者也不用改订单服务，同时峰值可以被缓冲。”

代价：“会变成最终一致，积分可能延迟；消息可能重复，需要业务唯一键幂等； 同一订单的多条消息要按订单 ID 分区保证顺序；还要运维积压、死信和重平衡。”

替代方案：“如果量很小、下游很少，直接同步调用或线程池更简单； 如果只是延迟任务，Redis ZSet 或 DB 轮询也够。MQ 不是默认答案。”

结论：“这个场景下游多、峰值明显、允许最终一致，所以值得上； 我会选 Kafka 或 RocketMQ，按订单 ID 做 key，消费端幂等，配死信和 lag 监控。”
