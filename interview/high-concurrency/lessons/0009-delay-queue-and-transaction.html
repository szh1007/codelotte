Lesson 09 · 经典场景

订单 30 分钟未支付：延迟队列与 Outbox

“订单超时取消”是延迟队列的经典题；再往下追问，就会碰到 “取消和支付同时发生怎么办”“DB 写成功但消息没发出去怎么办”。 这一课把这两个坑一起填上。

30 分钟 前置：Lesson 06–08 产出：延迟队列选型 + 幂等状态机

本课目标

  • 说出 Redis ZSet、RabbitMQ TTL+DLX、RocketMQ 延迟消息、DB 轮询四种方案的取舍。
  • 用状态机 + 条件更新解决“取消”和“支付”的竞态。
  • 用 Outbox 解决“DB 写成功但 MQ 没发出去”的双写不一致。

1. 场景：30 分钟未支付，取消订单并释放库存

订单创建后进入 WAIT_PAY，30 分钟内未支付则取消，释放库存和优惠券。 需求看似简单，实际有三个难点：

  1. 定时：30 分钟后触发，不能靠用户刷新页面。
  2. 竞态：取消和支付可能同时发生，只能有一个成功。
  3. 可靠：消息不能丢，重复触发要幂等。

2. 四种延迟队列实现

方案怎么做优点缺点 / 注意
Redis ZSet score = 执行时间戳，member = 订单 ID；轮询到期元素 简单、延迟低、量级可控 要自己保证“取出后只处理一次”；Redis 挂了要能恢复
RabbitMQ TTL + DLX 消息设 TTL，过期后进入死信交换机，消费者处理 成熟、支持单条确认 同一队列里不同 TTL 会队头阻塞；用每队列 TTL 或延迟插件
RocketMQ 延迟消息 发送时指定延迟级别/时间，到期投递 原生支持，运维简单 4.x 是固定级别；5.x 才支持任意时间
DB 轮询 按 expire_at 扫到期订单，条件更新后处理 最可靠、易对账 DB 压力；要索引、分批、SKIP LOCKED

Redis ZSet 的关键细节

# 下单时写入，score 是到期时间
ZADD delay:order <execute_at_ms> <order_id>

# 轮询到期任务
ZRANGEBYSCORE delay:order 0 <now_ms> LIMIT 0 100

# 取出后先原子删除，再处理；处理失败重新放回
# 多实例消费时，用 Lua 比较 member 后 ZREM，避免重复处理

不要用“先 ZRANGE 再 ZREM”两条命令，否则多个消费者可能拿到同一条。 删除和领取要原子；处理失败要重新入队，并设置最大重试次数。

RabbitMQ 的坑

在同一个队列里给每条消息设不同 TTL，RabbitMQ 只会在队头消息过期时处理， 后面的消息即使到期也要排队，造成延迟不准。正确做法是每个延迟时长一个队列， 或使用 delayed message exchange 插件。

3. 取消与支付的竞态：让状态机裁决

不要用“先查状态，再更新”的两步操作；两个请求可能同时查到 WAIT_PAY。 用条件更新让数据库裁决： 

-- 取消：只有仍处于待支付才取消
UPDATE orders
SET status = 'CANCELLED'
WHERE id = ? AND status = 'WAIT_PAY';

-- 支付：只有仍处于待支付才支付
UPDATE orders
SET status = 'PAID'
WHERE id = ? AND status = 'WAIT_PAY';

两条 SQL 只有一个能影响 1 行。取消成功后再释放库存/优惠券；支付成功后再发支付事件。 如果取消赢了，支付回调要识别“订单已取消”，走退款或失败处理。 所有后续动作都要幂等：重复取消、重复释放库存不能产生副作用。

面试一句话

“延迟队列只负责‘到点触发’，不负责‘一定只触发一次’。 正确性靠状态机 + 条件更新 + 幂等，而不是靠 MQ 的 exactly-once。”

4. Outbox：解决 DB 与 MQ 的双写不一致

下单成功后要发 OrderCreated。如果先写 DB 再发 MQ，发 MQ 失败就漏消息； 如果先发 MQ 再写 DB，DB 失败就发了不存在的订单。这就是双写问题。

本地事务写订单 + 写 outbox
→
Relay读 outbox 发 MQ
→
标记已发送或重试
→
消费者幂等处理
BEGIN;
INSERT INTO orders (...) VALUES (...);
INSERT INTO outbox (aggregate_id, event_type, payload, status)
VALUES (?, 'OrderCreated', ?, 'PENDING');
COMMIT;

-- Relay 独立进程/线程：
SELECT * FROM outbox
WHERE status = 'PENDING'
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;

-- 发 MQ 成功后：
UPDATE outbox SET status = 'SENT' WHERE id = ?;
  • 业务数据和 outbox 在同一个本地事务里，保证“要么都写，要么都不写”。
  • Relay 至少一次发送；消费者必须幂等，所以重复没关系。
  • 可以用 CDC（如 Debezium）监听 outbox 表，省掉轮询。
  • outbox 表要定期清理，避免无限增长。

5. 分布式事务：先问“能不能不做”

方案一致性代价适用
2PC 强一致 阻塞、协调者单点、性能差 少量强一致、内部系统
TCC 最终一致 要写 Try/Confirm/Cancel 三个接口，业务侵入大 资金、库存等需要预留资源
Saga 最终一致 要设计补偿动作，补偿也可能失败 长流程、跨服务编排
事务消息 最终一致 依赖 MQ 支持（如 RocketMQ） 本地事务 + 发消息
Outbox 最终一致 多一张表、Relay、清理 大多数“DB + MQ”场景

面试里最稳的立场：能通过业务设计避免分布式事务，就不要上； 必须跨服务时，优先 Outbox/事务消息 + 幂等 + 补偿，而不是硬上 2PC。

2 分钟口述练习

面试官问：“订单 30 分钟未支付自动取消，怎么设计？” 请按“延迟方案 → 竞态 → 幂等 → 双写兜底”回答。

展开参考答案

延迟方案：“量不大用 Redis ZSet，score 存到期时间，轮询取出到期订单； 要更可靠就用 RocketMQ 延迟消息或 DB 轮询，按团队运维能力选。”

竞态：“取消时执行 UPDATE ... WHERE status='WAIT_PAY'， 支付也做同样的条件更新；只有一个能成功。取消成功后再释放库存和优惠券。”

幂等：“延迟消息可能重复，取消和释放库存都要幂等； 用状态机保证已取消的订单不会再次取消，库存只回补一次。”

双写兜底：“下单写 DB 和发 MQ 用 Outbox，同一个本地事务写业务表和 outbox， Relay 至少一次发送；消费端幂等。这样不会出现订单写了、消息没发的情况。”

收尾：“延迟队列只负责触发，正确性靠状态机、条件更新和幂等； 同时监控延迟、失败重试和死信。”
