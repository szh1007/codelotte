RDB、AOF、主从、Sentinel、Cluster：把 Redis 讲成一套系统

会写 GET/SET 只是入门。面试官追问“Redis 挂了怎么办”时， 他要听的是持久化、复制、故障切换和分片这四层，而不是“重启一下”。

1. 持久化：RDB 与 AOF 的取舍

维度RDBAOF
记录什么 某一时刻的数据快照 写命令日志（追加）
恢复速度 快，直接加载快照 慢，要重放命令；7.0 多部分 AOF 有优化
数据丢失 可能丢失最后一次快照之后的数据 取决于 fsync：always 最安全，everysec 最多约 1 秒
对性能影响 fork 子进程 + copy-on-write，瞬间内存和 IO 压力 持续写盘；always 模式延迟明显
适用 缓存、可重建数据、备份 对丢失敏感、能接受更大文件和恢复时间

AOF 的 appendfsync 三档：

  • always：每条写命令都 fsync，最安全，性能最差。
  • everysec：每秒 fsync，默认档；故障时最多丢约 1 秒。
  • no：交给操作系统，性能最好，丢失窗口不可控。
工程选择

缓存类数据：可以只开 RDB，甚至不持久化，挂了从 DB 重建。 会话/计数等“丢了会疼”的数据：AOF everysec + RDB 备份 + 副本。 要求 RPO 接近 0：AOF always，但同时要接受写延迟；并且要明白 Redis 复制默认是异步的，持久化不等于强一致。

Redis 4.0 起支持混合持久化：AOF 重写时前半段用 RDB 格式，后半段追加增量命令， 兼顾恢复速度和丢失窗口。Redis 7.0 使用 multi-part AOF（base + 多个增量文件 + manifest）。

2. 主从复制：读扩展与故障基础

主从复制默认是异步的：主节点处理完写就返回，再异步把命令发给从节点。 从节点可以分担读流量，但可能读到旧数据；主节点挂了，未同步的写可能丢失。

  • 全量同步：从节点首次连接，主节点生成 RDB 发给它，再补发增量命令。
  • 部分重同步：网络短暂断开后，靠 replication backlog、replid 和 offset 补发缺口，避免每次全量。
  • 复制延迟：从节点 INFO replication 看 offset 差；读己之写场景要读主库或做会话粘滞。
  • WAIT：可以让主节点等待 N 个副本确认，但它不是强一致协议，故障切换仍可能丢数据。
主从不是高可用

主从只解决“有副本、能读扩展”。主节点挂了，谁来把从节点提升为主？ 这需要 Sentinel 或 Cluster 的故障转移。

3. Sentinel：不负责分片，只负责“谁是新主”

Sentinel 是一组独立进程，监控主从节点；主节点不可用时，Sentinel 之间投票， 选出一个从节点提升为主，并通知客户端新地址。

  • 至少 3 个 Sentinel，且部署在不同故障域，避免“裁判一起挂”。
  • quorum 决定“多少个 Sentinel 认为主挂了才触发选举”；真正切换还需要多数派授权。
  • 客户端通过 Sentinel 查询当前 master 地址，不能写死 IP。
  • Sentinel 不做数据分片；数据量/吞吐超过单机时要用 Cluster。

4. Cluster：16384 个槽的分片世界

Redis Cluster 把 key 空间分成 16384 个 hash slot， 每个 key 用 CRC16 取模落到某个槽，槽再分配给主节点。每个主节点可以带从节点做副本。 

slot = CRC16(key) mod 16384

  • 至少 3 主 3 从，才能容忍单主故障并保持多数派。
  • 节点间用 gossip 传播集群状态；客户端收到 MOVED（槽已迁移）或 ASK（迁移中临时重定向）。
  • 扩容/缩容本质是迁移槽，不是搬整个库；迁移期间要注意热 key 和大 key。
  • 多 key 操作、事务、Lua 脚本要求 key 在同一槽；跨槽要么拆业务，要么用 hash tag。
  • Cluster 自带故障转移，通常不再需要 Sentinel。

5. 内存满了：淘汰策略

设置 maxmemory 后，达到上限时按 maxmemory-policy 处理：

  • noeviction：不淘汰，写命令报错（读还能用）。适合不能丢的数据，但要监控和扩容。
  • allkeys-lru / allkeys-lfu：所有 key 里按最近最少使用/最不常用淘汰。缓存常用。
  • volatile-lru / volatile-lfu / volatile-ttl：只在设置了 TTL 的 key 里淘汰。
  • allkeys-random / volatile-random：随机淘汰，简单但命中率不稳定。

LRU 是近似实现（采样若干 key），LFU 更适合“曾经很热、现在不热”的访问模式。 面试里要补一句：淘汰策略是兜底，不是容量规划；根本办法是拆 key、设 TTL、扩容/分片。

面试官问：“如果 Redis 整个集群挂了，你们的系统会怎样？怎么处理？” 请按“影响 → 检测 → 降级 → 恢复 → 防再发”回答。

展开参考答案

影响：“先区分用途。缓存挂了，读请求会打到 DB，可能把 DB 拖垮； 锁/限流挂了，会影响写路径和入口保护；会话挂了，用户可能掉登录。 所以不同用途要有不同的降级策略。”

检测：“客户端超时和错误率上升，Sentinel/Cluster 触发故障转移； 监控看 Redis 连接数、错误率、DB QPS 和 P99。”

降级：“缓存场景启用本地缓存和限流，非核心功能关闭， 核心读走 DB 但限流；锁场景退化为 DB 唯一约束/乐观锁； 会话场景允许重新登录或读备用存储。”

恢复：“故障转移完成后，先预热热点 key，再逐步放量； 检查数据丢失窗口，用 DB 或 MQ 对账修复；重复消费靠幂等兜底。”

防再发：“主从 + Sentinel 或 Cluster、多可用区部署、容量留余量、 定期故障演练；持久化按 RPO 选 AOF everysec/always，并做备份恢复演练。”
