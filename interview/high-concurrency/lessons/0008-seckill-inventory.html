Lesson 08 · 经典场景

秒杀系统：把 10 万 QPS 挡在数据库之前

秒杀是面试里的“综合大题”：缓存、MQ、限流、幂等、库存、对账全都能串起来。 这一课给你一套从入口到 DB 的分层答法，并标出每一步的失败窗口。

35 分钟 前置：Lesson 03、06、07 产出：3 分钟白板方案

本课目标

  • 按“客户端 → 网关 → 应用 → Redis → MQ → DB → 对账”分层设计秒杀。
  • 用 Redis Lua 原子完成“查库存 + 防重复 + 扣减”，并说清为什么必须原子。
  • 讲清超卖、少卖、Redis 成功但 MQ 失败、DB 失败等异常怎么兜底。

1. 先定义问题：秒杀到底难在哪

  • 瞬时流量极高：平时 1 千 QPS，活动开始瞬间 10 万 QPS。
  • 不能超卖：库存 100 件，绝不能卖出 101 件。
  • 要防重复：同一用户刷接口，不能买多次。
  • 要公平/防机器人：不能全被脚本抢走。
  • 要扛住失败：Redis、MQ、DB 任一环节抖动，系统不能雪崩。

核心思路只有一句：把绝大多数请求挡在 DB 之前，只让少量请求走到落库。

2. 分层架构：每一层只做一件事

客户端 / CDN静态页、倒计时、按钮置灰
→
网关鉴权、限流、黑名单、验证码
→
应用校验、Redis Lua 扣减
→
MQ异步下单、削峰
→
DB条件扣减 + 唯一约束
  1. 客户端：活动页静态化走 CDN；倒计时结束才允许点击；点击后按钮置灰，防连点。
  2. 网关：登录校验、按用户/IP/设备限流、黑名单、验证码/答题，把机器人和刷子挡在外面。
  3. 应用：校验活动状态、库存预热、执行 Redis Lua；成功才发 MQ，失败直接返回售罄/重复。
  4. MQ：把“创建订单”异步化，消费者按 DB 能承受的速率处理；消息按用户/商品 key 分区。
  5. DB：最终扣减用条件更新，唯一索引防重复；失败进入重试/死信/对账。

3. Redis Lua：查库存、防重复、扣减，一步原子完成

-- KEYS[1] = stock:sku:1001
-- KEYS[2] = buyers:sku:1001
-- ARGV[1] = user_id
-- 返回：>=0 剩余库存；-1 售罄；-2 重复购买

local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
    return -1
end

if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2
end

redis.call('SADD', KEYS[2], ARGV[1])
redis.call('DECR', KEYS[1])
return stock - 1

Python 侧调用：

result = redis.eval(script, 2, stock_key, buyers_key, user_id)
if result >= 0:
    mq.send("seckill.order", {"sku": sku, "user_id": user_id})
elif result == -1:
    return {"code": "SOLD_OUT"}
else:
    return {"code": "DUPLICATE"}
为什么必须 Lua

“GET 判断库存 → 再 DECR”是两条命令，中间可能被其他请求插队，导致超卖。 Lua 在 Redis 里原子执行，把“查、判重、扣减、记录用户”合成一个不可分割的操作。 单独用 DECR 只能防超卖，防不了同一用户重复购买。

库存预热与 key 设计

stock:sku:1001          # 库存
buyers:sku:1001         # 已购买用户集合
seckill:activity:888    # 活动状态

活动开始前把库存从 DB 预热到 Redis，并设置合理 TTL；活动结束后清理。 不要等第一个请求来了才回源，否则会把 DB 打穿。

4. MQ 异步下单与 DB 最终扣减

消费者拿到消息后：

BEGIN;
-- 1. 条件扣减，防超卖
UPDATE stock
SET stock = stock - 1
WHERE sku_id = 1001 AND stock >= 1;

-- 2. 唯一索引防重复：(user_id, activity_id)
INSERT INTO seckill_order (user_id, activity_id, sku_id, status)
VALUES (?, ?, ?, 'CREATED');
COMMIT;
  • 如果 UPDATE 影响 0 行：DB 侧已无库存，说明 Redis 与 DB 不一致，记录异常并补偿。
  • 如果 INSERT 唯一键冲突：说明重复消费，直接当成功处理（幂等）。
  • DB 成功后，订单状态从 CREATED 进入待支付；失败进入重试队列/死信。

5. 失败窗口与兜底

失败点后果处理
Redis 扣减成功，MQ 发送失败 用户看到“抢到”，但订单没创建 发送重试 + 本地消息表/Outbox + 定时对账
MQ 消费失败/重复 订单漏建或重复建 重试、死信、唯一索引幂等
DB 扣减失败（无库存） Redis 多扣了 回补 Redis 库存（补偿）或标记异常人工对账
Redis 整体挂了 无法预扣，流量直打 DB 限流 + 降级为“排队/售罄”，保护 DB

超卖和少卖的取舍：宁可少卖，不可超卖。少卖可以回补/人工处理， 超卖要赔偿用户和品牌。所以 Redis 预扣 + DB 条件扣减双保险，DB 失败时优先保护不超卖。

6. 热点库存：一个 key 打满一个分片

所有请求都操作 stock:sku:1001，这个 key 只能落在一个 Redis 分片上， 单分片被打满。常见解法：

  • 库存分桶：把 1000 件拆成 10 个 key，每个 100 件；请求按用户哈希到某个桶，桶空再尝试其他桶。复杂度上升，需要汇总和对账。
  • 本地库存：应用实例预分配一小部分库存，先在本地扣，再异步同步；要处理实例故障导致的库存丢失。
  • 请求合并：同一商品的并发请求在应用层合并成一次 Redis 操作（singleflight）。
  • 限流与排队：前端排队/令牌，控制进入 Redis 的速率。
不要用 hash tag 解决热 key

Redis Cluster 的 {sku:1001} hash tag 会把相关 key 放到同一个槽， 对多 key 操作方便，但会让热点更集中。热 key 要拆，不是绑在一起。

7. 防机器人：技术之外的一层

  • 验证码、答题、滑块；设备指纹、行为风控。
  • 按用户/IP/设备多维限流；黑名单和信誉分。
  • 预约/抽签制：把“先到先得”改成“资格 + 抽签”，从根上削峰。
  • 前端结果轮询，避免长时间占用连接。

3 分钟白板练习

面试官说：“设计一个 10 万 QPS 的秒杀系统，库存 1000 件，不能超卖， 同一用户限购 1 件。请从入口到落库讲一遍。”

展开参考答案

入口：“活动页静态化走 CDN；网关做登录、限流、验证码和黑名单； 前端按钮置灰防连点。先把机器人和重复点击挡掉。”

预扣：“活动前把库存预热到 Redis。请求进来执行 Lua： 查库存、SISMEMBER 判重、SADD 记录用户、DECR 扣减，一次原子完成。 返回售罄或重复就直接结束，不碰 DB。”

异步：“Lua 成功后发 MQ，按商品/用户 key 分区； 消费者创建订单，DB 用 stock >= 1 条件更新 + (user_id, activity_id) 唯一索引做最终防超卖和幂等。”

异常：“Redis 成功但 MQ 失败，用发送重试 + 本地消息表/Outbox； DB 无库存就回补 Redis 或标记异常；Redis 挂了就限流降级，宁可少卖不超卖。”

热点与对账：“单 key 热就分桶/本地库存/请求合并； 活动结束做 Redis 与 DB 对账，补漏单和回补库存。全程监控 QPS、售罄率、 MQ lag 和 DB 错误率。”
