1. 架构：一张图

Producer批量、按 key 选分区
→
Partition有序追加日志，leader 读写
→
ISRfollower 同步副本
→
Consumer Group按 offset 拉取
  • Topic 逻辑类别；Partition 物理有序日志，是并行和有序的单位。
  • Offset 消费者位置；提交 offset = 处理进度。
  • Consumer Group 同一分区只给一个消费者；不同 group 各消费全量。
  • ISR 与 leader 同步的副本集合；HW 高水位，消费者只能读到已提交消息。
  • KRaft 新版本的元数据模式，替代 ZooKeeper。

2. 关键配置

配置常用值作用/取舍
acksallISR 全部确认；可靠性最高，延迟最高
replication.factor3副本数；容忍 1–2 个 broker 故障
min.insync.replicas2至少 2 个 ISR；不足时拒绝写，避免静默丢
unclean.leader.election.enablefalse不让落后副本当 leader；牺牲可用性保数据
enable.idempotencetrueproducer 重试去重（PID + 序列号）
enable.auto.commitfalse手动提交，处理成功后再 commit
max.poll.interval.ms按处理时长两次 poll 的最大间隔；超时会踢出 group 触发 rebalance
session.timeout.ms10–30s心跳超时；太短易误判，太长故障发现慢
auto.offset.resetearliest/latest没有已提交 offset 时从哪开始
max.poll.records按处理能力一次 poll 的消息数；太大易超 max.poll.interval
经典组合

RF=3 + min.insync.replicas=2 + acks=all + unclean=false：挂 1 个 broker 继续写，挂 2 个拒绝写以保数据。

3. 投递语义

语义做法结果
At most once先 commit offset，再处理可能丢，不重复
At least once处理成功后 commit；失败重试不丢，可能重复（默认）
Exactly once幂等 producer + 事务 + read_committedKafka 内部不重不丢；外部系统仍需幂等

exactly-once 的边界：Kafka 事务覆盖“读 Kafka → 处理 → 写 Kafka”； 如果写 MySQL/Redis/第三方 API，需要幂等 sink、事务消息或 Outbox。

4. 不丢 / 不重 / 有序

不丢：三段检查

  1. Producer：acks=all、重试、enable.idempotence=true、合理 delivery.timeout。
  2. Broker：RF=3、min.insync=2、unclean.leader.election=false、磁盘/ISR 监控。
  3. Consumer：关闭自动提交，处理成功后 commit；失败重试/死信。

不重：消费端幂等

  • 业务唯一键 + 唯一索引（如 order_id）。
  • 去重表：处理前插入 message_id，冲突则跳过。
  • 状态机条件更新：WHERE status='WAIT_PAY'。
  • 版本号/乐观锁：旧版本不覆盖新版本。

有序

  • 同一业务 key 发到同一分区（默认按 key 哈希）。
  • 一个分区同一时刻只被一个消费者处理。
  • 不追求全局有序；全局有序 = 单分区 = 吞吐上限。
  • 消费端并行处理会破坏顺序；要顺序就单线程处理该分区，或按 key 内部串行。

5. 积压处理

看 lag生产 offset − 消费 offset
→
定位突增 / 消费慢 / 分区倾斜
→
扩容消费者 ≤ 分区数
→
兜底降级 / 转存 / 死信
  • 消费者数超过分区数不会提升并行度，只会多空闲实例。
  • 增加分区会改变 key 的分区映射，影响既有顺序；高峰期慎用。
  • 先优化消费逻辑里的同步慢调用，再考虑加消费者。
  • 积压严重可临时转存到新 topic/对象存储，先恢复主链路。
  • 持续监控 lag、消费耗时、失败率、死信量。

6. Rebalance

  • 触发：消费者加入/离开、分区变化、心跳超时、max.poll.interval.ms 超时。
  • 影响：分区重新分配，期间消费暂停；频繁 rebalance 会导致重复消费和延迟。
  • 优化：cooperative sticky 分配、static membership、合理 session timeout、减小 max.poll.records、把长处理异步化。

7. 选型对比

KafkaRabbitMQRocketMQ
模型分区日志，pull队列/交换机，可 push分区队列，pull
强项高吞吐、保留/重放、流处理灵活路由、低延迟、单条 ack、DLX事务消息、延迟消息、顺序消息

# topic
kafka-topics.sh --create --topic orders --partitions 6 \
  --replication-factor 3 --bootstrap-server localhost:9092
kafka-topics.sh --describe --topic orders --bootstrap-server localhost:9092

# 生产/消费
kafka-console-producer.sh --topic orders --bootstrap-server localhost:9092
kafka-console-consumer.sh --topic orders --from-beginning \
  --bootstrap-server localhost:9092 --group demo

# 消费组与 lag
kafka-consumer-groups.sh --describe --group demo --bootstrap-server localhost:9092
kafka-consumer-groups.sh --reset-offsets --to-earliest \
  --group demo --topic orders --execute --bootstrap-server localhost:9092

9. 面试一句话

Kafka 为什么快？
顺序追加写、page cache、批量压缩、零拷贝、分区并行、pull 背压。
分区的作用？
并行单位 + 有序单位；分区内有序，全局有序要单分区。
怎么保证不丢？
producer acks=all+重试+幂等；broker RF=3+min.insync=2+unclean=false；consumer 处理后再 commit。
怎么保证不重？
默认 at-least-once，消费端幂等：唯一键/去重表/状态机/版本号。
exactly-once 边界？
Kafka 内部事务链路成立；外部系统要幂等 sink/事务消息/Outbox。
怎么保证顺序？
同 key 同分区，单消费者单分区处理；不追求全局有序。
积压怎么办？
看 lag 定位；扩消费者≤分区数；加分区/批处理/异步；降级/转存/死信。
rebalance 原因？
成员变化、心跳超时、poll 超时、分区变化；用 cooperative/static/合理超时优化。
Kafka vs RabbitMQ？
Kafka 高吞吐日志/重放；RabbitMQ 灵活路由/单条 ack/低延迟。
为什么用 MQ？
解耦、异步、削峰；代价是最终一致、重复、顺序、运维复杂度。
