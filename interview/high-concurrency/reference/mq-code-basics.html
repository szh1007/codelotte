MQ 在代码里长什么样

你的理解基本正确：生产者是代码调用客户端库往 broker 写消息，消费者是代码调用客户端库取消息并执行。 需要补三件事：MQ 是异步的、消费者是你的应用而不是 Kafka、 Topic/Partition 是集群资源。这一页用 Python 代码把它们对齐。

1. 心智模型：没有“直接调用”

生产者应用调用 Producer SDK
→
Broker把消息追加到 Topic/Partition
→
消费者应用调用 Consumer SDK 拉取
→
你的 handler执行业务逻辑

Kafka 不是 RPC：生产者发完消息不会等消费者执行，broker 只是把消息存进日志。 消费者什么时候处理、处理多久，由消费者应用决定。

一句话

Broker 只负责存和转发；执行业务代码的是消费者应用。 所谓“消费者”，不是一个 Kafka 进程，而是一段调用 Consumer SDK 的你的代码。

客户端库（SDK）替你做很多事：连接 broker、拉取元数据、按 key 选分区、批量发送、重试、 消费者组协调、提交 offset。你只需要配置和写业务 handler。

2. 生产者代码：往 topic 写一条消息

以 Python 的 confluent-kafka 为例（生产环境常用；asyncio 场景可用 aiokafka）：

import json
from confluent_kafka import Producer

producer = Producer({
    "bootstrap.servers": "localhost:9092",  # broker 地址
    "acks": "all",                          # 等 ISR 确认，偏可靠
    "enable.idempotence": True,             # 重试不产生重复
})

def on_delivery(err, msg):
    if err:
        print("发送失败:", err)
    else:
        print(f"已写入 {msg.topic()}[{msg.partition()}] offset={msg.offset()}")

producer.produce(
    topic="orders",          # topic 名只是字符串
    key="order-123",         # 同一个 key 默认进同一分区
    value=json.dumps({"order_id": "order-123", "amount": 99}),
    callback=on_delivery,
)
producer.flush()             # 等发送完成；进程退出前要调用
  • bootstrap.servers：客户端先连其中一台，再自动发现整个集群。
  • produce(topic, key, value)：SDK 根据 key 算出分区，发给该分区的 leader。
  • callback：异步回调，告诉你写入哪个分区、offset 是多少，或者失败原因。
  • flush：等待缓冲区里的消息发完；不调用可能丢未发送的消息。
消息不是“对象”

Kafka 只存字节。JSON、Avro、Protobuf 都只是你和消费者约定的序列化格式； 生产者和消费者必须用同一套格式，否则消费者解析会失败。

3. 消费者代码：拉取、执行、提交 offset

import json
from confluent_kafka import Consumer

consumer = Consumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "order-workers",       # 同一 group 分担分区
    "auto.offset.reset": "earliest",   # 没有已提交 offset 时从头读
    "enable.auto.commit": False,       # 处理成功后再手动提交
})

consumer.subscribe(["orders"])

def handle(payload):
    print("执行业务逻辑:", payload)

try:
    while True:
        msg = consumer.poll(1.0)       # 拉取一条，超时 1 秒
        if msg is None:
            continue
        if msg.error():
            print("consumer error:", msg.error())
            continue
        try:
            handle(json.loads(msg.value()))
            consumer.commit(message=msg)   # 成功后才提交 offset
        except Exception as e:
            print("处理失败，不提交，等待重试/死信:", e)
finally:
    consumer.close()
  • group.id：同一个 group 的消费者分担 topic 的分区；不同 group 各自消费全量。
  • subscribe：订阅 topic；具体分到哪个分区由 Kafka 的组协调器决定。
  • poll：主动拉取消息；Kafka 是 pull 模型，消费者能控制速率。
  • commit(message=msg)：处理成功后提交 offset；先处理再提交 = at-least-once，可能重复，所以 handler 要幂等。
面试一句话

“消费者不是 Kafka 替我执行任务，而是我的应用 poll 到消息后调用自己的 handler； 处理成功再提交 offset，失败就不提交，靠重试和幂等兜底。”

5. Topic / Partition 怎么创建

Topic 是逻辑名字，Partition 是物理上的有序日志。它们通常是集群级资源， 由运维/管理员在创建 topic 时定好，而不是生产者每发一条消息临时创建。

方式一：CLI（最常见）

# 创建：6 个分区，3 副本
kafka-topics.sh --create \
  --topic orders \
  --partitions 6 \
  --replication-factor 3 \
  --bootstrap-server localhost:9092

# 扩容分区：只能增加，不能减少
kafka-topics.sh --alter \
  --topic orders \
  --partitions 12 \
  --bootstrap-server localhost:9092

方式二：代码里的 AdminClient（也能创建，但属于管理动作）

from confluent_kafka.admin import AdminClient, NewTopic, NewPartitions

admin = AdminClient({"bootstrap.servers": "localhost:9092"})

futures = admin.create_topics([
    NewTopic(
        "orders",
        num_partitions=6,
        replication_factor=3,
        config={"retention.ms": "604800000"},  # 保留 7 天
    )
])
for topic, future in futures.items():
    try:
        future.result()
        print("created", topic)
    except Exception as e:
        print("create failed", topic, e)

# 扩容分区：12 是新的总数，不是“再加 12 个”
admin.create_partitions([NewPartitions("orders", 12)])
三个边界
  • 分区只能增不能减；副本数调整更复杂，通常通过分区重分配工具。
  • 增加分区会改变 key 的分区映射，同一个 key 的新旧消息可能落到不同分区，顺序保证会被打破；高峰期不要随手加。
  • 不要依赖自动创建：broker 的 auto.create.topics.enable=true 会用默认分区/副本数创建，容易埋坑；生产一般关闭。

6. key、partition、consumer group 的关系

keyorder-123
→
partitionhash(key) % 分区数
→
group一个分区只给一个消费者
→
顺序只保证分区内
  • 同一个 key 默认进同一分区，所以同一订单/同一会话的消息能按顺序消费。
  • 一个分区同一时刻只会分给同一个 group 里的一个消费者；消费者数超过分区数，多出来的空闲。
  • 不同 group.id 各自消费全量：审计、计费、报表可以各用一个 group。
  • 生产者可以显式指定 partition=0，但容易造成热点；一般让 key 哈希决定。
  • 消费者想直接消费某个分区，可以 assign([TopicPartition("orders", 0)])，绕过组协调，通常用于特殊场景。

7. RabbitMQ 的写法：拓扑常在代码里声明

RabbitMQ 和 Kafka 的代码风格不同：exchange、queue、binding 这些拓扑，经常在应用启动时 用代码声明（幂等，重复声明不会重复创建）；Kafka 的 topic/partition 更像集群资源，通常由运维/AdminClient 管理。 

import pika

connection = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
channel = connection.channel()

# 声明队列；durable=True 表示 broker 重启后队列还在
channel.queue_declare(queue="tasks", durable=True)

channel.basic_publish(
    exchange="",
    routing_key="tasks",
    body=b'{"task_id": "t-1"}',
    properties=pika.BasicProperties(delivery_mode=2),  # 消息持久化
)
connection.close()
def callback(ch, method, properties, body):
    handle(body)
    ch.basic_ack(delivery_tag=method.delivery_tag)  # 处理成功才确认

channel.basic_qos(prefetch_count=10)  # 未确认消息上限，控制背压
channel.basic_consume(queue="tasks", on_message_callback=callback)
channel.start_consuming()

RabbitMQ 常见的是“push 给消费者回调 + 单条 ack”；Kafka 是“消费者 pull + 提交 offset”。 两者本质一样：客户端库负责通信，你的代码负责处理。

8. 本地跑通（最小验证）

# 1. 启动单节点 Kafka
docker run -d --name hc-kafka -p 9092:9092 apache/kafka:4.4.0

# 2. 创建 topic（单节点副本数只能 1）
docker exec -it hc-kafka /opt/kafka/bin/kafka-topics.sh \
  --create --topic orders --partitions 3 --replication-factor 1 \
  --bootstrap-server localhost:9092

# 3. Python 依赖
pip install confluent-kafka

# 4. 先跑 consumer.py，再跑 producer.py；观察 offset 和分区

如果宿主机 Python 连不上 9092，先用容器内的 console producer/consumer 验证 topic 是否正常； 多节点/生产环境需要显式配置 advertised.listeners。

9. 面试一句话

生产者/消费者是 SDK 吗？
是客户端库；它通过 Kafka 协议连 broker，替你处理分区、批量、重试、组协调和 offset。
消费者是 Kafka 在执行任务吗？
不是；broker 只存消息，消费者应用 poll 到消息后执行自己的 handler。
Topic/Partition 在代码里定义吗？
topic 名在代码里引用；分区/副本通常在创建 topic 时由 CLI/AdminClient/控制台设置。
分区数能改吗？
只能增加，不能减少；增加会改变 key 映射，可能破坏同一 key 的顺序。
消息怎么保证同一订单有序？
用订单 ID 做 key，同一 key 进同一分区；一个分区只给一个消费者处理。
RabbitMQ 和 Kafka 代码上最大区别？
RabbitMQ 拓扑常在代码里 declare，push + 单条 ack；Kafka topic 多由运维建，pull + offset。
