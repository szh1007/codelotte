12 个经典高并发场景

每个场景给一套 30–60 秒的答题骨架，再列关键取舍和常见追问。 面试前不要通读，挑 2–3 个最可能问的，出声说一遍。

1. 秒杀 / 库存扣减 2. 订单超时取消 3. 缓存与 DB 一致性 4. 排行榜 5. 点赞 / 计数 6. 接口限流 7. 消息积压 8. 重复消费 / 幂等 9. 分布式锁 10. Feed 流 / 时间线 11. 大促削峰 12. AI Agent 高并发

1. 秒杀 / 库存扣减

30 秒骨架
  1. 入口挡：CDN 静态页、验证码、网关按用户/IP 限流、按钮置灰。
  2. Redis 预扣：Lua 原子完成查库存、判重、扣减、记录用户。
  3. MQ 削峰：扣减成功才发消息，异步创建订单。
  4. DB 兜底：条件更新 stock >= 1 + 唯一索引 (user_id, activity_id)。
  5. 对账降级：Redis/DB 对账、回补库存；Redis 挂了限流降级，宁可少卖不超卖。

关键取舍：Redis 预扣保证性能，DB 条件更新保证正确性；少卖可补，超卖不可接受；热 key 用分桶/本地库存/请求合并，不要用 hash tag 绑在一起。

常见追问：Redis 扣成功但 MQ 失败怎么办？→ 发送重试 + Outbox/本地消息表 + 对账。库存分桶怎么汇总？→ 各桶扣减后汇总，活动结束对账。

2. 订单超时取消

30 秒骨架
  1. 延迟方案：Redis ZSet（score=到期时间）、RabbitMQ TTL+DLX、RocketMQ 延迟消息、DB 轮询，按规模和运维选。
  2. 到期处理：UPDATE ... WHERE status='WAIT_PAY' 条件更新，只有一个请求能成功。
  3. 资源释放：取消成功后释放库存/优惠券，动作幂等。
  4. 支付竞态：支付也做条件更新；支付赢了取消影响 0 行，取消赢了支付走退款/失败。
  5. 可靠性：至少一次触发 + 幂等；失败重试/死信；DB 兜底扫描。

关键取舍：延迟队列只负责“到点触发”，不保证只触发一次；正确性靠状态机 + 条件更新 + 幂等。

常见追问：Redis ZSet 怎么只消费一次？→ Lua 原子领取/删除，失败重入队。RabbitMQ 同队列不同 TTL？→ 队头阻塞，按延迟分队列或用插件。

3. 缓存与 DB 一致性

30 秒骨架
  1. 先问要求：能接受秒级旧数据，还是必须强一致？
  2. 常规方案：cache-aside；更新 DB 后删缓存，不直接更新缓存。
  3. 并发回填：延迟双删，或订阅 binlog 发 MQ 删缓存，value 带版本号。
  4. 读己之写：写后短时间读主库，或写后主动删缓存。
  5. 强一致：缓存不承担正确性，用 DB 事务/唯一约束/乐观锁；TTL 永远兜底。

关键取舍：删缓存比更新缓存简单且幂等；延迟双删降低概率但不是强一致；binlog 方案更可靠但更重。

常见追问：为什么先更新 DB 再删缓存？→ 反过来旧值更容易被回填。缓存挂了怎么办？→ 限流回源 + 本地缓存 + 降级。

4. 排行榜

30 秒骨架
  1. 结构：ZSet，member=用户/作品，score=分数。
  2. 写：ZINCRBY 更新分数；高频写入可先本地聚合再批量写。
  3. 读：ZREVRANGE 取 Top N；分页用 ZREVRANGE start stop 或按分数游标。
  4. 同分：score 相同按 member 字典序；需要业务规则就拼复合 score 或二次排序。
  5. 规模：大 ZSet 拆分/分页缓存/离线快照；热榜结果缓存几秒。

关键取舍：ZSet 适合实时 Top N，不适合海量历史明细；榜单可接受秒级延迟，用缓存挡读。

常见追问：百万用户榜单怎么扩容？→ 分片榜单 + 合并 Top N；或离线计算 + Redis 只存结果。

5. 点赞 / 计数

30 秒骨架
  1. 去重：Set like:post:{id} 存用户，SADD/SISMEMBER/SREM。
  2. 计数：SCARD 或 String INCR/DECR；两者要一致。
  3. 热度：ZSet hot:posts，ZINCRBY 加减分。
  4. 落库：点赞事件发 MQ，异步写 DB；(user_id, post_id) 唯一索引幂等。
  5. 热点：大帖 Set 分片/只保留近期；热帖本地缓存 + 请求合并。

关键取舍：Redis 做实时计数和去重，DB 做最终明细；允许点赞数短暂不一致，用对账修复。

常见追问：重复点赞怎么防？→ Set 天然去重 + DB 唯一索引。Redis 丢了怎么办？→ 从 DB 重建或接受降级。

6. 接口限流

30 秒骨架
  1. 维度：IP、用户、租户、接口、全局；不同维度不同阈值。
  2. 算法：允许突发用令牌桶；平滑用漏桶；简单用固定/滑动窗口。
  3. 层次：网关粗限流 + 应用细限流 + 本地桶兜底，Redis 共享状态。
  4. 反馈：429 + Retry-After；核心请求可排队，非核心直接拒绝。
  5. 兜底：Redis 故障降级本地限流；监控拒绝率和误杀。

关键取舍：阈值太松保护不了，太紧误杀；分布式限流依赖 Redis，必须设计降级。

常见追问：固定窗口边界双倍怎么办？→ 滑动窗口/令牌桶。多实例怎么共享？→ Redis Lua 原子扣减。

7. 消息积压

30 秒骨架
  1. 看 lag：生产 offset − 消费 offset，按分区看是否倾斜。
  2. 定位：生产突增、消费变慢、下游慢调用、分区数不足、rebalance 抖动。
  3. 扩容：消费者加到不超过分区数；必要时加分区（注意 key 顺序）。
  4. 提效：批量、异步化、优化慢 SQL/HTTP；消费端并行但要保序。
  5. 兜底：临时转存、降级非核心、死信、限流生产；事后补数据。

关键取舍：加消费者最快但有上限；加分区会改变 key 映射；转存能救主链路但增加复杂度。

常见追问：消费者超过分区数有用吗？→ 没有，多出来的空闲。积压时能丢消息吗？→ 非核心可丢/转死信，核心不能。

8. 重复消费 / 幂等

30 秒骨架
  1. 承认语义：大多数 MQ 是 at-least-once，重复不可避免。
  2. 唯一键：业务唯一 ID + DB 唯一索引，冲突即已处理。
  3. 去重表：处理前插入 message_id，失败回滚；或 Redis SETNX 短期去重。
  4. 状态机：条件更新 WHERE status='...'，只允许合法跃迁。
  5. 对账：定期核对消息与业务结果，补漏/纠错。

关键取舍：幂等要落在业务侧，不能依赖 MQ 的 exactly-once；去重表有存储成本，Redis 去重有丢失窗口。

常见追问：先提交 offset 还是先处理？→ 先处理再提交，接受重复；先提交会丢。幂等键怎么选？→ 业务唯一键，不是消息 ID。

9. 分布式锁

30 秒骨架
  1. 加锁：SET key token NX PX ttl，一条命令完成。
  2. 解锁：Lua 比较 token 后再 DEL，避免误删别人的锁。
  3. 续期：长任务 watchdog 续期；或拆短任务/设足 TTL。
  4. 正确性：Redis 锁适合效率；强正确性用 DB 唯一约束/乐观锁或 fencing token。
  5. Redlock：多节点多数派，有时钟/暂停争议；面试要能说出双方观点。

关键取舍：锁的粒度、TTL、续期、失败重试；锁越强，性能和复杂度越高。

常见追问：任务超时锁失效怎么办？→ 续期 + fencing token。Redis 主从切换丢锁？→ 异步复制导致，正确性不靠它。

10. Feed 流 / 时间线

30 秒骨架
  1. 推拉结合：普通用户写扩散（推），大 V 读扩散（拉）。
  2. 存储：收件箱用 Redis List/ZSet 存 feed ID，按时间排序。
  3. 读：取收件箱 ID，再批量取内容；分页用游标，不用 offset。
  4. 去重/排序：发布时间 + ID 复合 score；重复内容去重。
  5. 规模：大 V 粉丝多，推模式会写放大；冷用户延迟构建。

关键取舍：推模式读快写慢，拉模式写快读慢；大 V 是分水岭；缓存和分页策略决定体验。

常见追问：粉丝千万怎么推？→ 大 V 拉模式/异步推 + 收件箱合并。分页重复怎么办？→ 游标 + 去重。

11. 大促削峰

30 秒骨架
  1. 容量：按 10 倍峰值评估，压测核心链路，留 30–50% 余量。
  2. 入口：网关限流、验证码、静态页、非核心入口关闭。
  3. 缓冲：MQ 削峰，消费者按 DB 能力限速；队列长度和 lag 监控。
  4. 保护：熔断下游、降级非核心、超时预算、重试退避+jitter。
  5. 预案：开关、回滚、扩容、对账、故障演练。

关键取舍：削峰换来延迟和最终一致；限流会误杀；降级要提前设计开关，不能临时改代码。

常见追问：MQ 积压怎么办？→ 扩消费者/加分区/转存/降级。DB 扛不住？→ 限流 + 缓存 + 批量 + 分库分表（最后手段）。

12. AI Agent 高并发

30 秒骨架
  1. 量化：在线用户 ≠ QPS；估算活跃请求、LLM 调用频率、token 成本。
  2. 入口：网关鉴权 + Redis 租户令牌桶 + 配额，超限 429。
  3. 应用：FastAPI/uvicorn 多 worker，asyncio + 异步 LLM 客户端连接池，超时/取消。
  4. 缓存与异步：Redis 会话/精确响应缓存；Kafka 长任务、审计、用量事件；Kafka 不做请求-响应。
  5. 保护：LLM 供应商熔断 + 备用模型 + 队列背压 + 成本预算；监控 TTFT/tokens/成本/lag。

关键取舍：长 LLM 调用靠异步而非线程；语义缓存要租户隔离和阈值；成本是硬约束，必须做预算和降级。

常见追问：GIL 影响吗？→ I/O 等待释放，CPU 密集才受限。没用过 Redis/Kafka 怎么答？→ 诚实说设计过/本地跑过，讲取舍和失败场景。
