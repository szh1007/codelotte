# 11: 死循环三层防御

**What to build:** agent 会犯"钻牛角尖"的毛病——反复执行同一操作、或连续失败却不换策略。本票实现三层独立防御，每层可触发、可观测、有测试：① 工具层：连续 N 次完全相同的工具调用（同名同参）拦截并提醒模型"你在重复"；结果无进展检测（连续输出无实质差异）。② 推理层：连续 M 次工具失败（含权限拒绝与沙箱错误）→ 熔断当前回合。③ 规划层：把任务目标与硬约束以系统级消息重注入后继续，或温和终止交还用户。所有拦截作为事件写入会话，TUI 与 HTML 导出可见。

🗣 大白话：给爱钻牛角尖的 agent 装三道保险丝——第一道发现"你在同一个动作上打转"，第二道"连着失败就停下来"，第三道"把任务目标再念一遍给它听"。拦截全程留痕，既是安全也是演示素材。

## 实施记录（2026-10-17）

**模块**：新增 [guardrails.py](../../../../src/codelotte/guardrails.py)（纯状态机，不碰会话/网络）。
loop 在每次工具调用前后喂它，按结论记录事件；阈值来自 settings.json，`AgentLoop` 默认值兜底。

**阈值（settings.json，均为 2–100，未写用默认）**：

| 键 | 默认 | 语义 |
|---|---|---|
| `guardrailRepeatLimit` | 3 | 连续同名同参调用第 N 次被工具层拦截 |
| `guardrailStagnationLimit` | 2 | 同名同参连续 N 次结果完全相同时，拦截下一次 |
| `guardrailFailureLimit` | 3 | 连续 N 次工具失败后熔断本回合 |
| `guardrailPlanningLimit` | 2 | 工具层累计拦截 N 次后，规划层温和终止 |

**三层语义（对票据原文的实现解读）**：

- **工具层**：同名同参 = 工具名 + 参数规范化 JSON（键序无关）；被拦调用**不执行、不过权限层**，
  拦截说明作为工具结果回传模型。`stagnation` 只在**同一签名**上比较结果（忽略行尾空白与 CRLF）——
  这是刻意的保守选择：跨调用的"输出相同"可能只是批处理正常结果，误报代价高于收益。
  `repeat` 与 `stagnation` 都在第 3 次调用前拦截（默认值下），区别是原因更准确；用户调高
  `repeat` 时 `stagnation` 仍能更早兜住"结果不变"的打转。
- **推理层**：连续失败按**真正执行后 ok=False 的工具结果**统计，覆盖工具错误、权限拒绝、
  沙箱错误与参数畸形；**工具层拦截本身不计入**（那是层①的动作，交给层③处理，三层保持独立）。
  熔断在**整批 tool_calls 处理完之后**检查——保证每个 tool_call 都有 tool 应答（协议不破）。
  熔断后追加一条"总结现状"提醒，用 `tools=None` 再请求一次；若端点仍硬塞回 tool_calls，
  一律丢弃（否则会落成没有 tool 应答的孤立调用，`--continue` 恢复时请求非法）。模型总结
  照常落盘；`RunEnded.guardrail_stop="circuitBreaker"`，`-p` 打印原因并退出码 1（与迭代
  硬上限同口径：回合被强制结束就不是成功退出）。
- **规划层**：首次工具层拦截批次后，把**任务目标（本回合用户原话，≤1200 字符）+ 硬约束**
  作为提醒重注入后继续；之后累计拦截到 `planning` 阈值则温和终止（`guardrail_stop="planning"`）。
  即使首批就拦了多次，也先给一次重注入（"先提醒一次再谈终止"是刻意策略）。
  提醒用 `user` 角色而非 mid-conversation `system`：查证 DeepSeek/OpenAI 兼容端点对中途
  system 的接受度不一致（部分后端要求 system 必须在开头、部分直接忽略），用 user 是
  协议最稳的选择——语义仍是系统级提醒，且在记录里可完整审计。
- **恢复一致性**：提醒全文存进事件的 `injected` 字段；`messages_from_entries` 在记录位置把
  它作为 user 消息插回，`--continue` 重建的请求与实时逐条一致（有测试断言）。
- **计数按回合重置**：上一回合的重复/失败不牵连新任务；迭代硬上限仍是最后一道兜底
  （原"无限重复读同一个文件"的测试改为读不同文件，否则会先被工具层拦下——这是预期行为）。

**事件记录**：`event` + `kind="guardrail"`，字段 `layer`（tool/reasoning/planning）、
`guard`（repeat/stagnation/circuitBreaker/reinject/terminate）、`message`、计数与阈值；
重注入事件额外带 `injected`。工具层事件先于对应 `tool_result` 落盘。

**展示**：`display.guardrail_notice` 是 TUI 与导出的同一句话（`🛡 守护拦截（层）：…`）。
TUI 实时事件与 `--continue` 回放都以加粗黄提示挂进对话流；HTML 用 `marker warn` 高亮，
Markdown 用 `> 🛡 …`；`-p` 打 stderr 并在收尾报告终止原因。

**已知边界**：
- 规划层由工具层拦截驱动，不按迭代数独立触发——长任务只在真的打转时才被提醒（误报保护）。
- 熔断的总结调用在硬上限之后仍会发出一次（清理性质，`calls_made` 如实 +1）。
- 被工具层拦下的调用不经过权限层（它从未执行）；审计里仍有 `tool_call` + `event` + `tool_result`。
- 工具层只识别"同名同参"的重复；模型反复换参数但每次都失败，由推理层兜住。
