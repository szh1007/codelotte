# 12: 压缩 v1（双触发 + 结构化摘要）

**What to build:** 上下文快满时自动"折叠记忆"并继续工作。触发策略为双档：利用率约 60% 时在**任务边界**（用户消息位置或 git commit 点）软触发；约 85% 时硬触发（不等边界）。摘要为固定七项结构：任务目标 / 已完成事项 / 关键决策及理由 / 活跃约束 / 涉及文件清单 / 未解决问题 / 下一步；由同一模型生成。**硬约束在摘要之外额外重注入**（防止摘要过程把约束"润色"丢失）。压缩不是删除：在会话中新增一条 compaction 记录（摘要 + 保留边界指针），原始记录仍可寻址、随时可查。TUI 与 HTML 导出均显示"此处发生过压缩"。

## 实施记录（2026-10-17）

**模块**：新增 [compaction/](../../../../src/codelotte/compaction/)——`trigger.py` 纯判定（双触发/
任务边界/最小保留集/上下文大小恢复），`summarize.py` 七项摘要模板与压缩后上下文装配。
`session/context.py` 负责从记录重装配（最后一条 compaction 生效），`loop.py` 在**每次请求前**
调用压缩；`cli` 把 `spec.context_window` 同时传给 loop 与 TUI（与状态栏同源）。

**术语**：本票按 **run / turn** 两级描述——一个 run = 一次 `AgentLoop.run()`（用户一句话到
最终回答，可含多次模型调用）；一个 turn = 一次 assistant 回复 + 它声明的工具链。最小保留集是
run 的**最后一个 turn**，不是整个 run；否则单 run 长任务里的更早 turn 永远压不掉。

**触发语义**：
- 分子 = 上一次请求的**实际 input tokens**（恢复时取最后 usage，若其后有 compaction 则取其
  `estimatedAfterTokens`）；分母 = 用户级生效窗口。每次请求现算，不读历史百分比。
- 软触发（默认 60%，settings.json 可配）：取上次压缩之后、且不切掉最小保留集的**最新任务边界**（用户消息位置，或成功
  `git commit` 所属 assistant 消息位置——只留 tool_result 会缺 tool_call 声明者，请求非法）。
  没有新边界就等（不为了凑阈值切半条工具链）。
- 硬触发（默认 85%，settings.json 可配）：压到最小保留集（最近一个 turn：最近一条 assistant
  及其工具链；若最后一条是刚输入的用户消息，就保留它），不等边界。超过 100%（用户把窗口
  下调）天然命中硬触发。
- **阈值可配（用户追加）**：`compactionSoftThreshold` / `compactionHardThreshold`，比例口径，
  必须满足 `0.2 ≤ soft < hard ≤ 0.9` 且 `hard - soft ≥ 0.2`；只改一边时另一边用默认值，
  按生效值校验（跨字段校验在 `config.load_settings`）。
- 上次压缩之后没有新一轮 → 不重复压缩（避免在同一份上下文上打转）；起点在第一次压缩之前
  的边界不复用。
- 最小保留集 = 摘要 + 硬约束 + 最近一个 turn（最近一条 assistant 及其工具链）。压缩后估算仍 ≥ 窗口（或硬压后仍 ≥60%）时，在
  compaction entry 与事件里写 `warning`，界面明确提示"窗口配置小于最小保留集/已压到最小集"，
  不无限压、不假装达标。

**摘要与重注入**：
- 摘要由**同一个模型**生成：`tools=None`，请求 = 被压缩前缀 + 最后一条七项模板指令
  （任务目标 / 已完成事项 / 关键决策及理由 / 活跃约束 / 涉及文件清单 / 当前未解决问题 / 下一步）。
  摘要调用照常计价、落 usage，但**不落 assistant 消息**（元操作，不是对话）；端点若硬塞
  tool_calls 一律丢弃。
- 硬约束不交给摘要器：`COMPACTION_CONSTRAINTS`（复用 guardrails 的 HARD_CONSTRAINTS）作为
  独立文本存进 compaction entry，并在压缩后上下文里作为 **system 消息**的独立段重注入——
  即使摘要漏写约束也仍然生效。
- 压缩后装配：`system`（摘要 + 硬约束）+ 保留段；保留段以 assistant 开头时补一条 user 桥，
  保证请求从 user 开始；原件全部留在会话文件里，`compaction.firstKeptEntryId` 只影响后续请求。

**记录与展示**：`compaction` entry 字段：`summary`、`firstKeptEntryId`、`constraints`、
`mode`（soft/hard）、`window`、`beforeTokens`、`estimatedAfterTokens`、`summaryModel`、
`warning`。**百分比不落盘**（预置决策）：entry 不存 `utilization`，展示时由
`beforeTokens / window` 现算；运行时 `CompactionEvent` 才携带触发占比。TUI 里是黄色折叠块
`🗜 上下文压缩（…）`，展开看摘要；最小集 warning 在**折叠块外**挂一条提示，且标题带 ⚠，
默认可见。HTML 是 `details.compaction` 高亮块（warning 放在 details 外），Markdown 是
`### 🗜 …` + `> ⚠` + 围栏摘要；`-p` 打一行压缩报告（含 warning）。状态栏超窗文案改为
「超预算 X%」，压缩后用估算值、下一次真实 usage 到达即覆盖。

**已知边界**：
- 触发分子是"上一次请求的实际 usage"：一个 run 的第一条新用户输入在首次响应后才计入，
  因此可能晚一个请求触发；这是以 API usage 为准的代价（不拿字符估算冒充真实占用）。
- 摘要请求需要把被压缩前缀再发一次；硬触发切掉最近一个 turn，所以一般小于触发时的上下文，
  但若上下文已贴近官方窗口且前缀很大，摘要请求仍可能超窗（窗口配置建议留余量）。
- 七项结构靠 prompt 约束，不解析校验模型输出；摘要原样存储（可回查、可后续做 A/B）。
- 只有最后一条 compaction 生效；更早的压缩边界被新摘要吸收（新摘要的输入包含旧摘要）。
- 本票不提供"强制压缩 N 次"的外部 API（票据 13 的回归套件需要时另行加实验入口）。
- `AgentLoop` 不设测试专用参数：恢复时的初始 tokens 从会话里的最后 usage / compaction 估算读，
  测试也通过写入真实 usage 记录来构造场景（审查修正，遵守 SPEC 的两缝纪律）。
- 摘要为空时抛 `ProviderError` 终止本次调用，不把空摘要写进会话、也不假装压缩成功；这是
  可见失败，不是静默降级。
- `-p` 的压缩报告是 TUI/HTML 之外的额外透明性（同一事件、不同呈现），不改变退出码。

## 预置决策（2026-10-17 定，实现按此口径，别回头改）

- **触发分母 = 用户级生效窗口 `spec.context_window`**（用户写了 `contextWindow` 用其值，没写用随包官方上限；用户只能下调不能上调，所以有效值恒 ≤ 官方上限，安全）。**不要从 `Catalog`/`ModelInfo` 取**——那里只有随包值，用户下调后状态栏与压缩阈值会分家。
- **装配链**：`AgentLoop` 目前拿不到窗口值（cli 只传给了 TuiApp）——实现时由 cli 把 `spec.context_window` 传进 loop 构造，与状态栏同源。
- **百分比每次请求现算，不落盘、不进会话**：窗口是运行配置不是会话历史，`--continue` 恢复时用当前配置重判；触发点定在"装配下一次请求之前"（每次请求必经）。
- **超 100% 也是硬触发**：判定写 `usage ≥ 85%`（天然含超 100%），不许写成闭区间留死角。600k/50w = 120% 的场景 → 下个可压时机立即硬触发，压到软阈值（60%）以下再继续。超 100% 只是超**用户预算**，请求本身不会失败（真实上限仍是官方 1M）。
- **最小保留集下限**：摘要 + 硬约束 + 最近一个 turn（= 最近一条 assistant 及其工具链，不是整个 run）= 不可再压的下限；窗口小于该下限时压到最小集为止并**明确提示**（"窗口配置小于最小保留集，已压到 X"），不无限压、不假装达标。
- 展示语义：状态栏 `>100%` 超的是预算而非真实上限；实现时顺带把提示语义改为"超预算"（可考虑黄/红区分超预算与超官方上限）。
