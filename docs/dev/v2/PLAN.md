# codelotte v0.2.0 开发计划（PLAN）

> 技术规格：[SPEC.md](SPEC.md) · 票据：[tickets/](tickets/README.md) · ADR：0010–0012
> v0.1.x 计划归档在 [../v1/PLAN.md](../v1/PLAN.md)；v0.3.0 在 [../v3/PLAN.md](../v3/PLAN.md)。

## 1. 这是一条什么线

| 项 | 内容 |
|---|---|
| 是什么 | codelotte v0.2.0：新增 `codelotte serve` 运行形态，落地 Redis / Kafka / PostgreSQL，并产出对比实验 |
| 为什么 | CLI 形态下不存在并发与故障，缓存一致性、限流、削峰这些问题**不会发生**，也就无法验证 |
| 交付物 | 可运行服务 + 8 个 lab 的对比数据 + SPEC/PLAN/ADR + 面试话术 |
| 不做什么 | 内核改动、MCP/Skill（v0.3.0）、K8s、Grafana 面板、语义缓存 |

## 2. 交付原则（本次最重要的一条）

**全部票据完成并跑出数据后，才写入简历与面试材料。部分完成不对外。**

原因：中间件这类能力，讲一半比不讲更危险。面试官追一句「压测数据呢」「消费者挂了会怎样」，
半成品会当场露馅。所以本计划的验收标准不是「跑通了」，而是「有错误版本、有正确版本、
有量化对比、有故障演练记录」。

配套纪律：

- 每个 lab 必须有 `results.json`，且能一条命令复现。
- 每个数字必须来自脚本输出，不手抄、不估算。
- 错误版本与正确版本**同时保留在仓库里**——它们是证据，不是垃圾。

## 3. 施工顺序（依赖优先）

```
01 部署地基 ──► 02 serve 骨架 ──► 03 用户与鉴权 ──┬─► 04 限流与配额
                                                  ├─► 05 缓存三大问题 ──► 06 缓存一致性
                                                  ├─► 07 分布式锁
                                                  └─► 08 任务队列 ──► 09 消费语义 ──► 10 削峰与背压
                                                                          └──► 11 事件总线与异步汇总

10, 11 ──► 12 可观测性与故障注入 ──► 13 压测与实验报告
11     ──► 15 客户端与演示（远程 CLI + 单页 HTML）

13, 15 ──► 14 发布收口
```

- **01–03 是地基**，做完之前不动任何 lab：没有可运行的 serve，lab 里的代码就只是脚本，
  接不回主线。
- **04–07（Redis 线）与 08–11（Kafka 线）在 03 之后可以并行**，但建议按 04→05→06→07→08 顺序
  推进：缓存的三个问题会反复出现在后面的队列与对账里，先打通收益最大。
- **12 与 15 可以并行**（都只依赖 11），**13、14 必须串行**，它们是收口。

## 4. 阶段、票据与工时

| 阶段 | 票据 | 产出 | 估时 |
|---|---|---|---:|
| P0 地基 | 01 部署地基、02 serve 骨架 | `deploy/` 五服务起来；API 能提交并跑完一次 run | 5h |
| P1 身份与限流 | 03 用户与鉴权、04 限流与配额 | Key 鉴权、429/402、lab01 + lab05 数据 | 4h |
| P2 缓存 | 05 缓存三大问题、06 缓存一致性 | 穿透/击穿/雪崩、脏读对比数据 | 5h |
| P3 锁 | 07 分布式锁 | 死锁/误删/续租/fencing 四组对比 | 2h |
| P4 消息 | 08 任务队列、09 消费语义、10 削峰与背压 | 队列选型三版对比、丢/重/乱序修复、lag 曲线 | 7h |
| P5 事件 | 11 事件总线与异步汇总 | 用量聚合、账单重放 | 3h |
| P6 客户端 | 15 客户端与演示 | 远程 CLI、单页 HTML、事件编解码 | 5h |
| P7 收口 | 12 可观测性与故障注入、13 压测与报告、14 发布 | 指标、5 个故障演练、压测报告、README/话术 | 7h |
| | | **合计** | **38h** |

38h 是加入客户端后的完整口径。**时间充足时按全量做**；若必须压缩，砍 P2 的击穿实验
与 08 的 Redis Streams 版本，不要砍故障演练与压测——前者只影响一个论点，后者影响全部论点的可信度。

## 5. 压测口径

| 项 | 目标 |
|---|---|
| provider | **fake provider**（零成本、确定性）；真实模型只做 3 条端到端冒烟 |
| 提交接口 | P99 < 50ms（只入队，不执行） |
| 并发 run | 200（worker 可水平扩，受分区数限制） |
| 事件吞吐 | 5000 条/s |
| 队列 lag | 停止注入后 60s 内回落到 0 |
| 故障恢复 | 每个注入场景在 60s 内恢复正常服务 |

**这个口径必须写进报告**：用 fake provider 测的是 harness 与中间件的吞吐，不是模型速度。
真实模型压测会同时烧钱和撞配额上限，数字也不可复现。

## 6. 风险与应对

| 风险 | 应对 |
|---|---|
| 范围膨胀（想加的中间件越来越多） | 以 SPEC 的 Out of Scope 为准；新增场景必须先写 ADR |
| 环境问题（Kafka 起不来、Windows 卷权限） | P0 只做一件事：证明五服务能起来；起不来就换 KRaft 单节点镜像 |
| 实验写成教程、没有数据 | 每个 lab 的验收项强制包含 `results.json` 与一条失败断言 |
| 内核被悄悄改动 | 每个票据验收时跑 `git diff --stat src/codelotte/*.py`，除新增 `serve/` 外必须为空 |
| 单据半途而废 | 交付原则：不全部完成不对外；票据状态表如实反映进度 |
